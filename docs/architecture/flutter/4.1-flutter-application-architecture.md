---

## 1. Purpose

This document converts the established Flutter client architecture into the concrete application-structure baseline that implementation must follow.

The objective is to create a Flutter application that is:

- aligned with enterprise domain ownership;
- independent of backend implementation details;
- secure by default;
- testable;
- suitable for offline and limited-connectivity operation;
- capable of supporting AI Society interaction;
- capable of supporting Walk Mode without creating a second platform;
- maintainable as the platform grows;
- and ready for additional client capabilities without structural rewrites.

This document does not redefine enterprise domains, backend services, AI authority, or database ownership. Those remain governed by the existing architecture.

---

## 2. Architectural Rule

> **The Flutter application is a client of enterprise capabilities, not an owner of enterprise truth.**

The application may own presentation state, temporary interaction state and local UX behaviour. Authoritative business state remains on the backend.

No Flutter feature may bypass the governed API boundary to access databases or internal services directly.

## 4. Layering Inside a Feature

Each substantial feature should follow the same conceptual layering:

```text
Feature UI
   ↓
Feature Presentation / State
   ↓
Feature Application Logic
   ↓
Feature Domain Contracts
   ↓
Repository / Gateway Interfaces
   ↓
Core API / Persistence Infrastructure
```

A feature may contain only the layers it actually requires. The structure must not become ceremony for its own sake.

The important boundary is that presentation code does not become the location of enterprise business rules.

---

## 5. App Layer

The `app` layer owns application-wide composition and lifecycle concerns.

It is responsible for:

- application bootstrap;
- dependency composition;
- environment configuration;
- root navigation;
- global theme configuration;
- global error boundaries;
- application lifecycle handling;
- and top-level capability registration.

It must not contain feature-specific business rules.

---

## 6. Core Layer

The `core` layer contains cross-cutting infrastructure that can be shared by multiple features.

Examples include:

- HTTP transport;
- API client configuration;
- authentication/session infrastructure;
- secure storage adapters;
- connectivity monitoring;
- retry policy;
- request correlation;
- structured error handling;
- local persistence primitives;
- synchronization infrastructure;
- telemetry interfaces;
- logging abstractions;
- and security utilities.

Core infrastructure must remain generic enough that feature modules do not become tightly coupled to one another through infrastructure internals.

---

## 7. Shared Layer

The `shared` layer contains reusable presentation and client contracts that have legitimate cross-feature value.

Examples include:

- design-system components;
- common form controls;
- accessibility helpers;
- common loading/error/empty states;
- shared display models where appropriate;
- and reusable presentation utilities.

Shared code must not become a dumping ground for unrelated business logic.

A component belongs in `shared` only when it has a clear cross-feature reason to exist.

---

## 8. Feature Modules

Feature modules represent user-facing capabilities rather than backend infrastructure.

For example:

```text
features/basket/
├── presentation/
├── application/
├── domain/
└── data/
```

A feature owns its client-side representation and interaction flow while delegating authoritative decisions to backend capabilities.

Feature modules should communicate through explicit contracts rather than importing each other's internal implementation details.

---

## 9. Domain-Facing Client Models

Flutter models represent API/client contracts rather than database records.

The client must not mirror database schemas merely because those schemas exist on the backend.

For example:

```text
Backend database
      ↓
Backend domain
      ↓
API DTO
      ↓
Flutter client model
      ↓
UI representation
```

Each boundary may intentionally transform the representation.

This prevents accidental coupling between the client and backend persistence structures.

---

## 10. Repository Boundary

Features that consume server data should interact with repository or gateway interfaces rather than directly constructing HTTP requests inside widgets.

Conceptually:

```text
Widget
  ↓
Controller / State
  ↓
Repository
  ↓
API Client
  ↓
Backend
```

This provides:

- testability;
- replaceable data sources;
- controlled caching;
- offline support;
- consistent error translation;
- and separation between UI and transport concerns.

---

## 11. State Classification

Every significant piece of client state must have an explicit ownership classification.

### Server-authoritative

Examples:

- prices;
- inventory availability;
- order status;
- payment state;
- subscription state;
- delivery allocation;
- reward entitlement.

### Session state

Examples:

- current route;
- active checkout interaction;
- active AI conversation;
- Walk Mode session.

### Local preference state

Examples:

- language;
- accessibility preferences;
- notification preferences;
- selected store preference.

### Cached state

Examples:

- catalogue information;
- previously synchronised receipts;
- recently viewed products.

### Offline queue state

Represents operations deliberately approved for deferred submission.

The state category must be documented whenever ambiguity could affect correctness.

---

## 12. Navigation Architecture

Navigation represents user journeys, not backend service topology.

For example:

```text
Home
 ├── Discover → Product → Basket → Checkout → Order
 ├── Orders → Order Detail
 ├── Household → Pantry
 ├── AI → Shopping assistance
 └── Walk Mode → Store navigation
```

A route is never an authorization mechanism.

Protected destinations must still obtain authoritative authorization from the backend.

Deep links and external entry points must resolve through the same navigation and authorization boundaries.

---

## 13. Dependency Injection and Composition

Dependencies must be composed at application/bootstrap boundaries rather than constructed arbitrarily inside widgets.

Conceptually:

```text
App Bootstrap
     ↓
Infrastructure
     ↓
Repositories / Gateways
     ↓
Feature Application Services
     ↓
Presentation
```

This enables deterministic tests and prevents feature code from becoming coupled to concrete infrastructure implementations.

The selected dependency-injection mechanism is an implementation detail and must not alter these boundaries.

---

## 14. API Client Boundary

All network requests must pass through the governed client API layer.

The API layer is responsible for:

- authentication headers;
- request correlation;
- serialization/deserialization;
- timeout handling;
- structured errors;
- safe retry policies;
- idempotency support where required;
- API version compatibility;
- and transport-level observability.

Feature code must not implement its own HTTP conventions independently.

---

## 15. Offline Boundary

Offline support is implemented below feature presentation where practical.

```text
Feature
  ↓
Repository
  ├── Remote source
  └── Local source / queue
```

The repository decides whether an operation is:

- immediately executable;
- cache-readable;
- queueable;
- or server-only.

The UI must not claim successful enterprise completion merely because a local queue accepted an operation.

---

## 16. Authentication Boundary

Authentication state is an application concern, but authorization remains a backend concern.

The client must support:

- login/session establishment;
- session renewal;
- logout;
- expiry handling;
- revocation handling;
- secure credential/token storage;
- and authentication failure propagation.

No feature may embed its own independent authentication implementation.

---

## 17. Error Architecture

Errors must be represented structurally rather than interpreted through free-text message matching.

The client should distinguish at minimum:

```text
Validation
Authentication
Authorization
Conflict
Stale State
Network
Timeout
Unavailable
Payment
AI
Unknown
```

User-facing messages are presentation concerns. Machine-readable error codes drive application behaviour.

Unexpected errors must remain distinguishable from expected business failures.

---

## 18. AI Boundary

The `ai` feature is an interaction surface for governed AI capabilities.

It must not embed the enterprise AI Society as uncontrolled client-side agents.

```text
Flutter AI Feature
       ↓
AI Capability API
       ↓
AI Society
       ↓
Agents / Intelligence Engines
       ↓
Enterprise Capabilities
```

The client must clearly represent whether an AI interaction is:

- a recommendation;
- an explanation;
- an approval request;
- an action request;
- a confirmed action;
- or a failed action.

---

## 19. Walk Mode Boundary

Walk Mode is a feature module within the application, not a separate application architecture.

It may contain specialised client infrastructure for:

- maps;
- spatial rendering;
- product recognition interfaces;
- route presentation;
- live session state;
- and mode transitions.

It must consume authoritative store, product and inventory information through governed capabilities.

The three established modes remain:

1. Manual;
2. AI Assisted;
3. Autopilot.

User takeover must always be possible where required by the Walk Mode architecture.

---

## 20. Security Boundary

The Flutter application is an untrusted execution environment.

Therefore the application must never be relied upon as the sole enforcement point for:

- authorization;
- pricing;
- inventory;
- payment decisions;
- AI authority;
- fraud decisions;
- trust policy;
- or enterprise security policy.

Sensitive proprietary algorithms should remain server-side in accordance with the security and anti-replication architecture.

---

## 21. Testing Structure

Testing follows the same boundaries as implementation:

```text
test/
├── core/
├── shared/
└── features/
```

Tests should cover:

- unit behaviour;
- repository behaviour;
- state transitions;
- serialization;
- error translation;
- widget behaviour;
- accessibility;
- offline behaviour;
- synchronization;
- API integration;
- and end-to-end user journeys.

Tests must verify architectural boundaries, not merely visual output.

---

## 22. Architectural Constraints

The following are prohibited without an explicit architecture decision:

- direct database access from Flutter;
- feature-specific authentication implementations;
- duplicated authoritative pricing logic;
- duplicated authoritative inventory logic;
- client-only authorization enforcement;
- raw HTTP calls from presentation widgets;
- uncontrolled global mutable state;
- embedding backend secrets in the application;
- treating cached data as authoritative without validation;
- treating AI responses as proof of completed actions;
- and creating a separate client architecture for Walk Mode.

---

## 23. Implementation Sequence

Phase 4 implementation should proceed in this order:

1. Establish Flutter application shell.
2. Establish configuration and bootstrap.
3. Establish navigation boundary.
4. Establish dependency composition.
5. Establish API client boundary.
6. Establish authentication/session infrastructure.
7. Establish structured error handling.
8. Establish local persistence and secure storage abstractions.
9. Establish connectivity and synchronization infrastructure.
10. Establish shared design system.
11. Implement the first vertical feature slice.
12. Expand feature modules using the established pattern.

This sequence prevents individual screens from becoming the architecture by accident.

## 25. Definition of Done — Phase 4.1

Phase 4.1 is complete when:

- the Flutter application structure follows this baseline;
- application/core/shared/feature boundaries exist;
- dependency composition is explicit;
- navigation is separated from authorization;
- API access has a single governed boundary;
- state ownership is classified;
- offline state is separated from authoritative state;
- authentication is centralized;
- feature modules follow the agreed structure;
- and the first implementation can proceed without inventing a competing architecture.
