# Phase 4.3 — Flutter State, Dependency Injection & Feature Composition

## Status

Defined

## Purpose

This document establishes how the Flutter client manages application state, dependencies, feature boundaries, and composition without allowing presentation code to become coupled to infrastructure or domain implementation details.

## 1. Architectural Principles

The Flutter client follows these rules:

- UI widgets render state and dispatch user intent; they do not own business rules.
- Feature state belongs to the feature that owns the use case.
- Domain models are not API DTOs.
- Repositories expose application-facing contracts and hide transport/storage details.
- Dependency injection occurs at composition boundaries, not inside individual widgets.
- Infrastructure dependencies are replaceable without rewriting feature UI.
- Global mutable state is prohibited unless its lifecycle is genuinely application-wide.
- Authentication/session state is centrally coordinated but consumed through explicit application contracts.
- AI and Walk Mode capabilities are accessed through interfaces, not directly through provider/SDK implementations.
- State transitions must be deterministic, observable, and testable.

## 2. Feature Structure

Each major Flutter capability is organised as a bounded feature rather than a collection of globally shared screens.

A feature may contain:

```text
feature/
  data/
    dto/
    datasources/
    repositories/
  domain/
    models/
    repositories/
    usecases/
  presentation/
    pages/
    widgets/
    controllers/
    state/
```

Shared infrastructure belongs outside feature folders. Shared code is introduced only when multiple features genuinely require the same stable capability.

## 3. State Ownership

State is classified by lifecycle and ownership.

### Local UI state

Examples:

- expanded/collapsed controls
- temporary form input
- animation state
- transient visual selection

Local UI state remains inside the relevant widget/controller.

### Feature state

Examples:

- current basket
- product search results
- order history
- checkout session state
- notification preferences

Feature state is owned by a feature-level controller/notifier and exposed to presentation components through immutable state.

### Application state

Examples:

- authenticated session
- active household context
- selected store context
- connectivity status
- application configuration

Application state is managed centrally because multiple features legitimately depend on it.

### Ephemeral process state

Examples:

- active checkout workflow
- Walk Mode session
- AI conversation turn
- pending command

Ephemeral state must have explicit creation, cancellation, completion, and recovery semantics. It must not be disguised as permanent application state.

## 4. State Model

State objects should represent explicit states rather than relying on nullable fields whose meaning is ambiguous.

A typical asynchronous feature state is:

```text
Initial
  ↓
Loading
  ↓
Loaded ───────────────┐
  │                   │
  └── Refreshing ─────┘
  ↓
Failure (recoverable)
```

For consequential workflows, explicit state machines are preferred over boolean combinations such as `isLoading`, `hasError`, and `isComplete`.

## 5. Immutability

Feature state exposed to the UI must be immutable.

Rules:

- Do not mutate lists/maps held by state.
- Replace state with a new value when state changes.
- DTOs must not be retained as mutable application state.
- Domain objects returned by repositories must not be mutated by widgets.
- Collections exposed to presentation code should be unmodifiable or defensively copied.

## 6. Dependency Injection

Dependencies are assembled at the application composition root.

```text
Composition Root
      │
      ├── Configuration
      ├── Auth/session
      ├── HTTP client
      ├── Local storage
      ├── Repositories
      ├── Use cases
      ├── Feature controllers
      └── Application router
```

Widgets receive the dependencies they need through the established DI/state mechanism rather than constructing repositories, HTTP clients, databases, or AI clients themselves.

## 7. Dependency Direction

The dependency direction is:

```text
Presentation
     ↓
Application / Use Cases
     ↓
Domain Contracts
     ↑
Data / Infrastructure Implementations
```

The presentation layer must never depend directly on:

- HTTP clients
- database clients
- PSP SDKs
- AI provider SDKs
- platform-specific storage implementations
- raw API DTOs

## 8. Repository Boundary

Repositories provide the stable client-side boundary between feature/application logic and infrastructure.

For example:

```text
ProductRepository
  ├── getProduct()
  ├── searchProducts()
  └── watchProductAvailability()
```

The implementation may use REST, GraphQL, local cache, offline storage, or another transport without changing consumers.

Repositories must not become general-purpose dumping grounds. A repository owns access to a domain resource; orchestration belongs in use cases/application services.

## 9. Use Cases

Use cases coordinate meaningful user/system actions.

Examples:

- AddProductToBasket
- RemoveBasketItem
- StartCheckout
- ConfirmCheckout
- GetOrderHistory
- RequestDeliveryUpdate
- StartWalkMode
- AskShoppingAssistant

A use case may coordinate multiple repositories or services. It must not contain presentation concerns.

## 10. Controller / Notifier Boundary

Controllers/notifiers translate UI intent into use-case execution and expose resulting immutable state.

```text
Widget
  ↓ user intent
Controller / Notifier
  ↓
Use Case
  ↓
Repository / Service
  ↓
Backend
  ↑
State result
  ↑
Controller / Notifier
  ↑
Widget
```

Controllers must not become second application-service layers. Business rules belong in the domain/application layer.

## 11. Caching

Caching is a data concern, not a reason to expose infrastructure to UI.

The repository may coordinate:

- memory cache
- persistent local cache
- network source
- cache invalidation
- stale-while-revalidate behaviour

The UI should receive a coherent domain/application state regardless of where the data originated.

## 12. Offline and Limited Connectivity

The state architecture must support limited-connectivity operation established by the platform architecture.

Features should distinguish:

- confirmed server state
- locally cached state
- pending local operation
- synchronisation failure
- conflict requiring resolution

A locally accepted operation must never be represented as server-confirmed unless the backend has actually acknowledged it.

## 13. Authentication and Session State

Authentication is application state with a dedicated boundary.

Consumers should depend on a session contract such as:

```text
SessionState
  unauthenticated
  authenticating
  authenticated
  expired
  signingOut
```

Feature code must not manually inspect raw access tokens or implement its own authentication lifecycle.

## 14. AI State Boundary

AI interactions are treated as explicit application capabilities.

The UI may request an AI capability through an interface such as:

```text
ShoppingAssistant
RecommendationEngine
HouseholdAssistant
WalkModeAssistant
```

The client does not embed proprietary AI orchestration, agent governance, decision policy, or intelligence-engine logic. Those remain backend responsibilities defined by the enterprise architecture.

AI responses must expose enough state for the UI to distinguish:

- requested
- processing
- response received
- action proposed
- action awaiting approval
- action executed
- action failed
- action cancelled

## 15. Walk Mode State Boundary

Walk Mode is an explicit session/process state machine, not ordinary screen navigation.

It must support the three established modes:

- Manual
- AI Assisted
- Autopilot

The client manages presentation, device capabilities, user takeover, and session state. Authoritative product, inventory, pricing, permissions, and consequential business decisions remain backend-controlled.

## 16. Navigation

Navigation responds to application state and user intent but does not become the owner of feature state.

Examples:

- unauthenticated → authentication flow
- authenticated → household/store context
- checkout confirmation → order result
- Walk Mode session → active Walk Mode surface

Deep links and notifications must resolve through the same application routing contracts rather than bypassing feature boundaries.

## 17. Error State

Errors must preserve structured information where available.

The client distinguishes at least:

- validation failure
- authentication failure
- authorization failure
- not found
- conflict/stale state
- connectivity failure
- timeout
- server failure
- cancellation

User-facing text is presentation content. Machine-readable error codes remain stable contracts.

## 18. Testing Requirements

Each feature should be testable at three levels:

### Unit tests

- state transitions
- use-case behaviour
- validation
- repository mapping
- error handling

### Integration tests

- repository + transport
- persistence + repository
- authentication/session integration
- offline synchronisation

### Widget tests

- rendering for each relevant state
- user intent dispatch
- loading/error/empty states
- accessibility-critical interaction

No feature should require a live backend merely to test its basic state transitions.

## 19. Observability

Controllers and use cases must expose meaningful lifecycle information to the established observability architecture without logging sensitive data.

At minimum, consequential operations should be traceable by:

- correlation/request identifier
- feature/use-case identifier
- operation outcome
- duration
- failure classification

Tokens, credentials, payment secrets, and sensitive household information must not be logged.

## 20. Architectural Guardrails

The following are prohibited:

- API calls directly from widgets.
- Repositories constructed inside widgets.
- Raw DTOs used as presentation state.
- Business rules hidden in UI callbacks.
- Global mutable feature state without an explicit lifecycle justification.
- AI provider SDKs imported into presentation code.
- Walk Mode business authority implemented solely on-device.
- Silent mutation of shared state.
- Treating cached data as confirmed server state.

## 21. Relationship to Previous Architecture

This document implements the Flutter client implications of:

- Enterprise Architecture
- Domain ownership
- API/service boundaries
- Authentication and authorisation
- Event-driven architecture
- AI Society architecture
- Intelligence Engine architecture
- Observability and trust architecture
- Walk Mode architecture

It does not redefine those enterprise decisions.

## 22. Result

Phase 4.3 establishes a Flutter architecture in which features remain independently testable and replaceable while sharing a coherent application composition model.

The client is therefore structured to consume the backend architecture rather than accidentally becoming a second source of business truth.
