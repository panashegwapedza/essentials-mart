# 4.5 — Error Handling & Resilience Architecture

**Status:** Accepted  
**Phase:** 4 — Flutter Application Architecture  
**Depends on:** 4.1 Flutter Application Architecture, 4.2 Client API Architecture, 4.3 State / Dependency Injection / Feature Composition, 4.4 Navigation & Application Shell  

## 1. Purpose

This document defines how the Flutter client handles failures without weakening the enterprise architecture, trust model, or user experience.

The client is responsible for presenting, recovering from, and safely propagating failures. It is not the authority for business rules, financial truth, inventory truth, authentication policy, or AI decisions.

## 2. Architectural Principles

1. **Fail safely.** A failure must never silently create false state.
2. **Server authority wins.** The client must treat authoritative API responses and domain events as the source of truth for server-owned state.
3. **No invented success.** Optimistic UI may be used only where rollback is deterministic and safe.
4. **Retry deliberately.** Only operations known to be safe or idempotent may be automatically retried.
5. **Preserve user intent.** Recoverable failures should allow the user to retry without unnecessarily reconstructing the operation.
6. **Do not expose internals.** Raw exceptions, stack traces, infrastructure details, credentials, or security-sensitive information must not be shown to users.
7. **Observable failures.** Failures must produce sufficient structured telemetry and audit context for diagnosis without leaking sensitive data.
8. **Offline is a state, not an exception.** Limited connectivity must be represented explicitly and handled according to operation policy.

## 3. Failure Classification

The client normalises failures into stable categories rather than coupling UI behaviour to arbitrary server messages.

| Category | Meaning | Default client behaviour |
|---|---|---|
| Authentication | Session/token is missing, expired, or rejected | Refresh when safe; otherwise transition to signed-out state |
| Authorisation | User lacks permission | Show access-denied state; do not retry automatically |
| Validation | Request is invalid | Show actionable validation feedback |
| Conflict | Server state changed or operation conflicts | Refresh authoritative state and ask user to retry where appropriate |
| Not Found | Requested resource no longer exists or is unavailable | Remove stale local reference and show appropriate state |
| Rate Limited | Server requests slower access | Honour retry metadata/backoff; avoid request storms |
| Network | Connectivity, timeout, DNS, transport failure | Enter recoverable connectivity state and retry only when policy permits |
| Server | Unexpected 5xx or unavailable dependency | Preserve user state, surface temporary failure, retry safely |
| Unknown | Unclassified failure | Fail closed, log structured diagnostic context, present generic recovery UI |

## 4. API Error Contract

The client consumes the API's stable machine-readable error code separately from its human-readable message.

The error code determines behaviour; the message is presentation material and may be localised or changed by the server.

The client must not infer domain semantics by matching error-message strings.

For example:

- `NOT_FOUND` → resource unavailable
- `STALE_PRICE` → refresh checkout state
- `PRODUCT_UNAVAILABLE` → refresh product/inventory state
- `UNAUTHENTICATED` → authentication recovery
- `VALIDATION_ERROR` → correct input

Unknown error codes must be handled safely as an unknown failure rather than causing a client crash.

## 5. Retry Policy

Retries are operation-specific.

### Automatically retryable

Only requests that are explicitly idempotent or have an idempotency mechanism may be automatically retried. Typical examples include safe reads and selected idempotent synchronisation operations.

### Conditionally retryable

Writes such as checkout, payment initiation, order creation, and delivery commands require an idempotency key or equivalent server-side deduplication before automatic retry is permitted.

### Never blindly retry

The client must not blindly repeat a financial or state-changing command merely because the network response was lost.

If the outcome is uncertain, the client queries authoritative server state instead of assuming failure and repeating the operation.

## 6. Timeouts and Backoff

Network operations use bounded timeouts appropriate to the operation type.

Retryable failures use bounded exponential backoff with jitter. The client must respect server-provided retry information when available.

The retry mechanism must have a finite attempt budget and must never create an uncontrolled request loop.

## 7. Offline and Limited Connectivity

Essentials Mart must remain useful under unreliable connectivity.

The client distinguishes:

- online;
- temporarily offline;
- degraded connectivity;
- synchronising;
- synchronisation failed.

Read-only cached experiences may remain available offline where the underlying data is explicitly marked as cacheable.

State-changing operations are queued only when their command semantics explicitly permit offline execution. Financial, security-sensitive, and otherwise non-deferrable operations must remain server-authoritative.

Queued commands must carry an idempotency identity and observable lifecycle state so the user can understand whether an action is pending, completed, failed, or requires intervention.

## 8. State Recovery

When a server response invalidates local assumptions, the client must reconcile against authoritative state.

Examples:

- stale product price → refresh product/checkout state;
- unavailable product → update basket presentation and notify the user;
- expired authentication → recover the session or return to authentication;
- conflict during checkout → reload the checkout session rather than mutating local state to force success.

Local state must never be edited merely to make an error disappear.

## 9. UI Error Boundaries

Failure handling occurs at appropriate layers:

- **application shell:** global failures and unrecoverable startup errors;
- **feature boundary:** feature-specific failures;
- **screen/component:** local rendering or interaction failures;
- **data layer:** transport, parsing, caching, and synchronisation failures.

A failure in one feature must not unnecessarily terminate unrelated application functionality.

Fatal startup failures use a safe recovery screen with retry/restart guidance. Diagnostic details remain available to telemetry rather than being displayed to the user.

## 10. Authentication Failure Handling

Authentication failures must fail closed.

The client must never:

- fabricate an authenticated state;
- silently downgrade to development authentication;
- persist invalid credentials as valid;
- expose access tokens in UI or logs.

Session refresh is attempted only through the approved authentication mechanism. If recovery fails, protected state is cleared according to the authentication architecture and the user is returned to the appropriate authentication flow.

## 11. Financial and Commerce Operations

Commerce operations receive stricter failure treatment.

For checkout, payment, refunds, and orders:

1. preserve the user's last known state;
2. identify whether the outcome is known or uncertain;
3. never duplicate a financial command because of an ambiguous transport failure;
4. query authoritative state where outcome uncertainty exists;
5. surface pending states explicitly;
6. record the operation identity needed for audit and reconciliation.

The Flutter client does not decide whether money was charged, an order was created, or inventory was committed.

## 12. AI and Walk Mode

AI-assisted operations follow the same resilience rules as ordinary operations, with additional safeguards.

An AI recommendation or action must not be represented as completed until the authoritative operation succeeds.

For Walk Mode:

- loss of connectivity must not cause fabricated navigation or inventory state;
- stale product/inventory information must be visibly treated as stale where relevant;
- autonomous actions must pause when required authority or connectivity is unavailable;
- user takeover must always remain available;
- safety-critical uncertainty defaults to a non-action state.

## 13. Telemetry and Auditability

Client failures should emit structured diagnostic events containing appropriate correlation identifiers, operation type, failure category, and safe contextual metadata.

Sensitive values must be redacted.

Client telemetry supports observability and diagnosis but does not replace the authoritative server audit trail defined by the enterprise architecture.

## 14. Error Presentation

User-facing error messages must be:

- understandable;
- actionable where possible;
- localisable;
- free of stack traces and infrastructure details;
- consistent across the application.

A user should generally see an action such as **Retry**, **Refresh**, **Sign in again**, **Review basket**, or **Contact support**, rather than an internal exception description.

## 15. Dependency Direction

The resilience architecture follows the existing Flutter dependency boundaries:

```text
UI / Feature
    ↓
Application State / Use Case
    ↓
Repository / API Client
    ↓
Transport / Platform
```

Errors are translated as they cross boundaries. UI code must not depend directly on HTTP implementation details.

## 16. Architectural Invariants

The following are mandatory:

- no HTTP status logic based on free-text messages;
- no automatic retry of non-idempotent commands without deduplication;
- no client-side invention of authoritative business state;
- no silent authentication downgrade;
- no sensitive information in user-facing errors or telemetry;
- no uncontrolled retry loops;
- no destructive local reconciliation merely to hide server failure;
- uncertain financial outcomes must be reconciled against server state.

## 17. Relationship to Existing Architecture

This document implements the client-side resilience consequences of the enterprise architecture and must remain aligned with:

- Enterprise Event-Driven Architecture;
- API & Service Architecture;
- Identity, Authentication & Authorisation;
- AI Society Architecture;
- Human-in-the-Loop Architecture;
- Notification & Communication Architecture;
- Walk Mode / Living Digital Supermarket Architecture;
- Security & Anti-Replication Architecture;
- Observability, Auditability & Trust Architecture;
- Deployment & Environment Strategy.

It does not redefine those authorities.

## 18. Decision

Flutter adopts a **fail-safe, server-authoritative, operation-aware resilience model**. Errors are classified structurally, retries are controlled by idempotency and operation semantics, offline behaviour is explicit, and uncertain state is reconciled rather than guessed.

This provides the client with resilience without allowing it to become a second source of business truth.
