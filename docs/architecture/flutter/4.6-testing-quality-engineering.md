# 4.6 — Flutter Testing & Quality Engineering Architecture

**Status:** Accepted  
**Phase:** 4 — Flutter Application Architecture  
**Depends on:** 4.1 Flutter Application Architecture, 4.2 Client API Architecture, 4.3 State / Dependency Injection / Feature Composition, 4.4 Navigation & Application Shell, 4.5 Error Handling & Resilience

## 1. Purpose

This document defines the quality and testing architecture for the Essentials Mart Flutter client.

Testing is treated as an architectural control, not merely a pre-release activity. The test strategy must prove that the client respects domain ownership, API contracts, authentication boundaries, resilience rules, AI authority constraints, and Walk Mode safety requirements.

## 2. Quality Principles

1. **Test behaviour, not implementation details.**
2. **Test architectural boundaries explicitly.**
3. **Prefer deterministic tests.**
4. **Do not weaken production guarantees to make tests pass.**
5. **Every critical user journey must have an executable acceptance path.**
6. **Failures must be reproducible and diagnosable.**
7. **Security and authority rules are testable invariants.**
8. **The client must never be treated as the authoritative source of business truth merely because a test fixture says so.**

## 3. Test Pyramid

The Flutter test suite is organised into complementary layers:

```text
                    E2E / Acceptance
                  ───────────────────
                Integration / Contract
              ───────────────────────────
             Feature / State / Repository
           ────────────────────────────────
                 Unit / Pure Logic
        ─────────────────────────────────────
             Static Analysis / Architecture
```

No single layer is sufficient.

## 4. Unit Tests

Unit tests cover deterministic logic with minimal dependencies.

Examples include:

- value transformations;
- validation;
- state transitions;
- error classification;
- retry/backoff decisions;
- idempotency-key generation rules;
- navigation guards;
- permission/authority presentation rules;
- DTO/domain translation;
- formatting and localisation logic.

Unit tests should be fast and independent of network, real databases, device services, or wall-clock timing wherever practical.

## 5. Repository and Data-Layer Tests

Repositories and data sources are tested against their defined contracts.

Tests must verify:

- successful reads and writes;
- malformed responses;
- unknown API fields where forward compatibility is expected;
- missing required fields;
- authentication failures;
- conflict responses;
- timeout and transport failures;
- cache behaviour;
- synchronisation behaviour;
- offline transitions;
- stale-data handling.

Mocks may be used for deterministic unit tests, but critical contract behaviour must also be exercised against realistic API responses.

## 6. API Contract Tests

The client must remain aligned with the authoritative backend API contracts.

Contract tests verify:

- endpoint paths and methods;
- request shapes;
- response DTO shapes;
- machine-readable error codes;
- authentication requirements;
- pagination and filtering semantics where applicable;
- idempotency requirements for state-changing operations;
- version compatibility.

The client must not derive API behaviour from undocumented implementation details.

## 7. State and Feature Tests

Each feature's state machine must be tested through meaningful transitions rather than only checking widget output.

For example:

```text
Initial
  ↓
Loading
  ↓
Success ──────────────┐
  │                    │
  └── Refresh ─────────┘
  ↓
Failure → Retry
  ↓
Offline / Degraded
  ↓
Synchronising
```

Tests must cover valid transitions and explicitly reject invalid transitions.

A state object must never represent an operation as successful when its authoritative operation has failed or remains unresolved.

## 8. Authentication and Authorisation Tests

Authentication tests verify that the client:

- never treats an absent credential as authenticated;
- handles expired sessions safely;
- does not silently downgrade authentication;
- clears protected state when required;
- prevents protected screens/actions from executing without authority;
- handles refresh failure deterministically;
- does not expose credentials in logs or UI.

Authorisation tests must verify UI gating where appropriate, but server-side authorisation remains authoritative.

## 9. Resilience Tests

The resilience architecture defined in 4.5 must be executable through tests.

Required scenarios include:

- offline startup;
- network loss during a read;
- network loss during a write;
- timeout;
- retry exhaustion;
- rate limiting;
- authentication expiry during an operation;
- server 5xx;
- malformed response;
- conflict/stale state;
- recovery after connectivity returns.

Tests must ensure retry mechanisms cannot produce uncontrolled request loops.

## 10. Commerce and Financial Safety Tests

Commerce operations receive a higher testing standard.

At minimum, tests must cover:

- basket ownership;
- price staleness;
- product availability changes;
- checkout retry behaviour;
- ambiguous network outcomes;
- duplicate submission protection;
- payment pending states;
- payment failure states;
- order reconciliation;
- refund status presentation.

A test must never assert that a financial operation succeeded merely because the client sent the request.

## 11. AI Society Integration Tests

The Flutter client does not own AI decision authority, but it must correctly represent governed AI actions.

Tests must verify:

- AI recommendations are distinguishable from authoritative outcomes;
- governed actions require the appropriate capability/authority;
- high-impact actions surface required human controls;
- denied actions remain denied;
- AI failures do not corrupt ordinary user workflows;
- AI-generated suggestions cannot silently mutate domain state;
- action status reflects server confirmation rather than model output.

## 12. Walk Mode Testing

Walk Mode requires dedicated testing beyond ordinary application UI tests.

The test suite must cover all three modes:

1. Manual.
2. AI Assisted.
3. Autopilot.

Required scenarios include:

- mode entry and exit;
- pause;
- user takeover;
- route recalculation;
- unavailable products;
- substitutions;
- basket mutation;
- stale inventory information;
- loss of connectivity;
- sensor/location failure;
- AI recommendation failure;
- user rejection of an AI suggestion;
- autonomous action requiring confirmation;
- audit attribution of material actions.

The critical invariant is that loss of connectivity, stale information, or uncertain authority must never cause the client to fabricate a successful autonomous action.

## 13. Widget and UI Tests

Widget tests verify presentation and interaction contracts without making them the only quality gate.

They should cover:

- loading/error/empty/success states;
- accessibility semantics;
- user actions;
- form validation;
- navigation outcomes;
- responsive layouts;
- permission-sensitive UI;
- offline indicators;
- pending/uncertain transaction states.

Tests should avoid over-coupling to incidental widget-tree structure so harmless refactoring does not create excessive maintenance cost.

## 14. Integration Tests

Integration tests exercise multiple layers together, such as:

```text
Screen
  ↓
Feature State
  ↓
Use Case
  ↓
Repository
  ↓
API Client
  ↓
Test Server / Controlled Backend
```

These tests prove that independently correct components remain correct when composed.

Critical integration paths include authentication, basket/checkout, order status, notifications, AI-assisted actions, and Walk Mode.

## 15. End-to-End Acceptance Tests

End-to-end tests represent complete user journeys on supported target environments.

Representative journeys include:

- sign in → browse → add to basket → checkout;
- recover from an expired session;
- recover from connectivity loss;
- view order after checkout;
- receive and act on a notification;
- use AI-assisted shopping;
- enter Walk Mode and take back control;
- complete a manually controlled shopping journey.

E2E tests must validate externally observable behaviour rather than internal implementation details.

## 16. Determinism and Test Isolation

Tests must be isolated from global mutable state.

The suite must avoid:

- shared mutable singleton state between tests;
- environment-variable mutation unless specifically testing process configuration;
- dependence on execution order;
- uncontrolled real-time delays;
- external provider availability;
- random identifiers without deterministic control.

Parallel execution must not change test outcomes.

## 17. Property and Invariant Testing

Where useful, invariant-oriented tests should verify properties that must always hold.

Examples:

- an unauthorised user cannot access protected data;
- an order cannot expose another customer's information;
- a failed operation cannot be represented as confirmed success;
- retrying an idempotent operation does not create duplicate effects;
- local state cannot override authoritative server state;
- an autonomous Walk Mode action remains attributable.

These tests are especially valuable for preventing regressions during refactoring.

## 18. Static and Architectural Checks

CI must perform static quality checks appropriate to the Flutter project, including:

- formatting;
- static analysis;
- type checking where applicable;
- unit tests;
- integration tests;
- architecture/dependency checks;
- generated-code consistency where applicable.

Architecture checks should prevent forbidden dependency directions, direct access to infrastructure from UI layers, and other established boundary violations.

## 19. Test Doubles and Production Parity

Test doubles must model the contracts they replace without inventing guarantees that production infrastructure does not provide.

A development adapter that lacks transaction isolation must not have tests claiming production-grade atomicity.

Conversely, important production guarantees must have tests against an implementation capable of providing those guarantees before those guarantees are considered complete.

This prevents false confidence from overly permissive mocks and in-memory adapters.

## 20. Security and Privacy Testing

Tests must verify that sensitive information does not cross intended boundaries.

Areas include:

- credential handling;
- token storage;
- logging redaction;
- API error presentation;
- local cache protection;
- screenshots/screen exposure where platform controls apply;
- analytics payloads;
- AI context minimisation;
- Walk Mode privacy controls.

Security tests complement, but do not replace, the enterprise security architecture and dedicated security testing.

## 21. Quality Gates

A Flutter change is not complete merely because it compiles.

For a change to pass its quality gate:

1. affected unit tests pass;
2. affected feature/state tests pass;
3. relevant API contract tests pass;
4. relevant integration tests pass;
5. security-sensitive changes receive the required security checks;
6. architecture boundaries remain intact;
7. formatting and static analysis pass;
8. critical user journeys remain valid;
9. failures remain observable and diagnosable.

The exact CI matrix may vary by change risk, but critical paths must not be excluded merely to shorten CI time.

## 22. Test Data

Test data must be synthetic or explicitly approved for testing.

Production customer, payment, household, location, or behavioural data must not be copied into ordinary development/test fixtures.

Fixtures should represent important edge cases, including empty states, unavailable products, stale prices, permission differences, connectivity failures, and partial/incomplete data.

## 23. Observability of Test Failures

Test failures must provide enough context to reproduce the failure without exposing secrets.

For integration and E2E failures, capture appropriate:

- operation identifiers;
- test scenario identifiers;
- relevant request/response metadata;
- state transition information;
- screenshots or diagnostics where supported.

Sensitive headers, tokens, payment credentials, and personal information must be redacted.

## 24. Architectural Invariants

The following are mandatory:

- tests must not create false architectural guarantees;
- critical domain authority must be tested at the authoritative boundary;
- financial outcomes must be reconciled rather than inferred;
- AI output must not be treated as authoritative completion;
- Walk Mode must preserve user takeover and auditability;
- test suites must be deterministic and isolated;
- production and test semantics must not silently diverge;
- security and privacy boundaries must be testable;
- a green test suite must represent meaningful coverage, not merely broad assertions.

## 25. Decision

Essentials Mart adopts a **layered, deterministic, contract-aware testing architecture** for Flutter.

Testing will verify not only that screens render, but that the client remains faithful to the enterprise architecture under normal operation, failure, degraded connectivity, AI assistance, and autonomous Walk Mode operation.

The quality system therefore becomes part of the platform's architectural safety mechanism rather than a final-stage checklist.
