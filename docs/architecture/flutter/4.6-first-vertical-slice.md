# Phase 4.6 — First Vertical Slice

**Project:** Essentials Mart  
**Phase:** 4 — Flutter  
**Section:** 4.6 — First Vertical Slice  
**Status:** Implemented  
**Reference capability:** Commerce Product → Basket  
**Date:** 2026-08-24

---

## 1. Purpose

Phase 4.6 takes one real Essentials Mart capability through the complete enterprise path:

```text
Flutter UI
    ↓
Feature state/controller
    ↓
Feature repository
    ↓
Governed API client
    ↓
Commerce HTTP API
    ↓
Commerce application service
    ↓
Commerce domain + repositories
```

This slice is the reference implementation pattern for subsequent Flutter capabilities.

---

## 2. Selected Capability

The first client capability is the **Product → Basket** journey:

1. Flutter requests the product catalogue.
2. The Commerce API returns explicit product DTOs.
3. Flutter maps those DTOs into client models.
4. The user adds an available product to the basket.
5. Flutter sends the authenticated basket command through the API client.
6. The Commerce API resolves the authenticated customer.
7. The Commerce application service validates the product and quantity.
8. The backend returns the authoritative basket representation.
9. Flutter updates presentation state from the server response.

This deliberately stops before payment and production checkout integration. Those remain later capabilities with stronger transactional and external-system requirements.

## 4. Backend Contract Used

The slice consumes the existing Commerce API:

- `GET /products`
- `GET /basket`
- `POST /basket/items`
- `DELETE /basket/items/{productId}`

Protected requests use the existing development authentication boundary only for local development. The Flutter client does not treat the development header as a production authentication mechanism.

The backend already owns product availability, basket ownership and business validation. The client only renders and requests actions.

---

## 5. Trust Boundaries

The client does not calculate or authoritatively decide:

- product availability;
- authoritative prices;
- basket ownership;
- checkout totals;
- order validity;
- authorization.

The Flutter application receives server state and presents it. The API remains the enterprise trust boundary.

---

## 6. Error Handling

The client consumes the API's machine-readable error contract through `ApiException`.

Transport failures are represented separately from HTTP/business errors. User-facing presentation uses the message supplied by the error boundary, while application behaviour can use the machine-readable code.

No client logic pattern-matches on backend free-text messages.

---

## 7. State Ownership

### Server-authoritative

- Product availability
- Product price
- Basket contents

### Client presentation state

- Loading state
- Error state
- Current displayed catalogue
- Current displayed basket count

The client does not persist an optimistic basket mutation as confirmed enterprise state. The basket is replaced with the server response after a successful command.

---

## 8. Why This Is the Reference Slice

This small journey exercises the important architecture without prematurely implementing every enterprise capability.

It demonstrates:

- Flutter application bootstrap;
- configuration;
- dependency composition;
- feature boundaries;
- API client boundary;
- session/auth boundary;
- DTO-to-model mapping;
- repository abstraction;
- presentation state management;
- structured error handling;
- backend domain ownership;
- server-authoritative state;
- and automated client tests.

Future features should copy the **pattern**, not the implementation details.

---

## 9. Explicit Non-Goals

This slice does not yet implement:

- production identity provider integration;
- secure production token storage;
- offline write queues;
- payment processing;
- inventory reservation;
- order history UI;
- AI Society interaction;
- Walk Mode;
- production persistence.

Those capabilities must enter through their existing architectural boundaries rather than being smuggled into this reference slice.

---

## 10. Definition of Done

Phase 4.6 is complete when:

- a Flutter app can start;
- the app reaches the Commerce API;
- products are retrieved through the governed API client;
- product responses are explicitly mapped into client models;
- an authenticated development customer can retrieve a basket;
- an available product can be added through the full API path;
- the resulting server-authoritative basket is rendered;
- API failures are represented structurally;
- no widget performs raw HTTP calls;
- and tests cover the client contract mapping.

This establishes the reference pattern for the remaining Phase 4 feature implementations.
