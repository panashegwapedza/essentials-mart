# Phase 4.2 — Client ↔ API Architecture

## Status

Accepted

## Purpose

Define the boundary between the Flutter application and Essentials Mart backend services before feature implementation begins.

## Architectural Rules

### 1. Transport boundary

Flutter communicates with backend capabilities through versioned HTTP APIs and their published contracts. UI widgets and feature state must not call transport clients directly.

The dependency direction is:

`Feature UI → Feature/Application State → Repository → API Client → HTTP API`

### 2. DTO boundary

Network DTOs are transport contracts. They must not be treated as domain entities.

Repositories translate DTOs into client-side domain models and translate domain commands into request DTOs. Internal server fields must never be exposed merely because they exist in a backend model.

### 3. Authentication

Authentication credentials are owned by the authentication boundary. Feature code must never manually construct authorization headers or access raw credential storage.

Expired credentials are handled centrally. A request that cannot be authenticated must fail through the standard authentication/error path rather than silently retrying with invalid credentials.

### 4. Error handling

API errors are represented by stable machine-readable error codes plus human-readable messages.

Client behavior must branch on the error code, not on message text.

Transport failures, authentication failures, validation failures, conflict responses, rate limiting, and server failures remain distinguishable to the application layer.

### 5. Retries

Retries are centrally controlled by the API client/repository boundary.

Only operations that are safe to retry may be automatically retried. Mutating requests require idempotency semantics before automatic retry is permitted.

The client must not blindly retry authentication, payment, checkout, order creation, or other externally consequential operations.

### 6. Idempotency

Operations capable of creating or changing externally consequential state must support idempotency where the backend contract requires it.

The client generates and preserves an idempotency key for the lifetime of a retryable operation. A retry must reuse the same key rather than create a new logical operation.

### 7. API versioning

The client targets an explicit API contract/version. Breaking server changes require a new version or a compatible migration path.

The Flutter application must not depend on undocumented response fields or implementation details.

### 8. Connectivity and offline behavior

The repository layer is the boundary for connectivity-aware behavior.

Read operations may use cached data where the feature explicitly permits stale data. Mutating operations must expose whether they were accepted by the server, queued locally, or failed.

The client must never represent locally queued work as server-confirmed state.

### 9. Synchronisation

Server state is authoritative for transactional resources. Local state is a cache, working state, or pending-operation representation as appropriate.

Synchronisation must be explicit and observable. Conflicts must be represented rather than silently overwritten.

### 10. Timeouts and cancellation

Every network operation must have bounded execution and support cancellation where the UI no longer requires the result.

A timeout is not equivalent to a confirmed failure of the server-side operation. For consequential operations, the client must use the backend's idempotency/status-recovery mechanism before attempting another operation.

### 11. Observability

Client requests must carry correlation/request metadata required by the platform observability architecture. Sensitive credentials and private user data must not be written to logs.

Errors surfaced to users may be friendly; diagnostic detail belongs in controlled telemetry.

### 12. AI boundary

AI features consume backend AI capabilities through explicit service contracts. Flutter does not contain proprietary intelligence-engine logic merely to make an interaction convenient.

AI recommendations and decisions must remain distinguishable from authoritative transactional state.

### 13. Walk Mode boundary

Walk Mode may consume live catalog, inventory, navigation, and AI capabilities through the same governed service boundaries. It must not bypass domain APIs or access operational databases directly.

Real-time updates are treated as asynchronous information and must not be mistaken for transactional confirmation.

## Request Lifecycle

A normal request follows:

`UI → State/Use Case → Repository → API Client → Auth → HTTP → API → DTO → Repository → Domain State → UI`

Failures return through the same boundary:

`HTTP/Transport Error → API Error Mapping → Domain/Application Error → UI State`

## Security Requirements

- No secrets in source control.
- No privileged backend credentials in the Flutter application.
- No direct database access from Flutter.
- No trust placed in client-side authorization decisions.
- No sensitive information in ordinary application logs.
- TLS is required for production communication.

## Consequential Operations

Checkout, order creation, payment initiation, payment confirmation, refunds, inventory-affecting commands, and other externally consequential commands require explicit server confirmation and appropriate idempotency/recovery semantics.

A client timeout must never be interpreted as proof that such an operation did not occur.

## Testing Requirements

The client/API boundary must be tested for:

- successful requests;
- authentication failure and credential refresh;
- validation errors;
- conflict responses;
- server failures;
- timeout and cancellation;
- retry behavior;
- idempotent retry behavior;
- malformed/unexpected responses;
- offline and reconnect behavior;
- DTO-to-domain mapping;
- prevention of accidental exposure of transport/internal fields.

## Relationship to Existing Architecture

This document implements the Flutter client boundary established by ADR-013 and remains subordinate to the enterprise API, security, observability, event, and domain architecture.

It does not redefine backend domain ownership, database boundaries, payment authority, inventory authority, or AI governance.

## Decision

Flutter will use a repository-mediated, contract-first API boundary with centralized authentication, typed error handling, controlled retries, explicit idempotency, versioned contracts, and authoritative server-state semantics.

This becomes the foundation for subsequent Flutter feature architecture and implementation.
