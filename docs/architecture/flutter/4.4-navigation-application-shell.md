# Phase 4.4 — Flutter Navigation & Application Shell Architecture

## Status

Defined

## Purpose

This document establishes the navigation and application-shell architecture for the Essentials Mart Flutter client.

The shell is responsible for composing application-wide navigation, session-aware routing, deep links, notifications, modal flows, connectivity-aware entry points, and feature surfaces without becoming the owner of feature business logic or state.

The shell must remain a thin orchestration boundary between application state and feature presentation.

## 1. Architectural Principles

The Flutter application follows these rules:

- Navigation is an application concern, not a business-rule engine.
- Feature modules own their screens, state, use cases, and presentation logic.
- The application shell owns only cross-feature composition and navigation policy.
- Route definitions are explicit and centrally discoverable.
- Authentication and authorization determine route accessibility, but widgets do not implement authorization rules.
- Deep links, notifications, and ordinary user navigation resolve through the same routing contracts.
- Navigation must be deterministic from application state and navigation intent.
- Consequential workflows must not be destroyed merely because a user navigates between surfaces.
- Modal, sheet, dialog, and full-screen presentation must have explicit ownership and lifecycle semantics.
- Offline and limited-connectivity states must not be confused with authenticated or authorized states.
- Walk Mode is a bounded session/process and must have a dedicated navigation surface without making the router its state owner.
- AI actions requiring user approval must return through explicit approval surfaces rather than silently navigating or executing consequential actions.
- Platform-specific navigation mechanisms remain implementation details behind the application routing contract.

## 2. Application Shell

The application shell is the stable outer structure of the Flutter client.

Conceptually:

```text
Application Bootstrap
        │
        ▼
Application Shell
        │
        ├── Session Boundary
        ├── Household / Store Context
        ├── Connectivity Boundary
        ├── Application Router
        ├── Global Overlay Host
        └── Feature Surface
                │
                ├── Home
                ├── Shopping
                ├── Basket
                ├── Orders
                ├── Household
                ├── Notifications
                └── Other bounded features
```

The shell may provide persistent UI such as navigation bars, drawers, global notification surfaces, or application-level overlays.

It must not contain feature-specific business rules.

## 3. Shell Responsibilities

The application shell is responsible for:

- bootstrapping the application router;
- observing application-level session state;
- selecting the appropriate authenticated or unauthenticated navigation tree;
- preserving the active application context where appropriate;
- providing global navigation surfaces;
- resolving deep links;
- resolving notification-driven navigation;
- presenting application-level error and recovery surfaces;
- coordinating connectivity-aware entry behaviour;
- providing a host for global, non-feature-specific overlays;
- entering and leaving bounded process surfaces such as Walk Mode;
- exposing navigation events to the established observability architecture.

The shell is not responsible for:

- calculating commerce totals;
- deciding whether a user is authorized to perform a domain action;
- owning basket, order, payment, or household business state;
- implementing AI orchestration;
- implementing Walk Mode authority;
- calling backend APIs directly from navigation code.

## 4. Navigation Hierarchy

The initial navigation hierarchy is organised around application state and bounded features rather than individual API endpoints.

```text
Root
├── Unauthenticated
│   ├── Welcome
│   ├── Sign In
│   ├── Registration
│   └── Account Recovery
│
└── Authenticated
    ├── Home
    ├── Shopping
    │   ├── Product Discovery
    │   ├── Search
    │   └── Product Detail
    ├── Basket
    ├── Checkout
    │   ├── Review
    │   ├── Confirmation
    │   └── Result
    ├── Orders
    │   ├── Order List
    │   └── Order Detail
    ├── Household
    ├── Notifications
    └── Walk Mode
        └── Active Session
```

This hierarchy is architectural rather than a commitment to a particular route package or URL syntax.

Individual features may introduce nested routes without bypassing their feature boundary.

## 5. Session-Aware Routing

Routing consumes the application session contract established in Phase 4.3.

The relevant session states are:

```text
Unauthenticated
      │
      ▼
Authenticating
      │
      ▼
Authenticated
      │
      ├── Expired
      │      │
      │      ▼
      │  Re-authentication
      │
      └── Signing Out
             │
             ▼
        Unauthenticated
```

The router must not infer authentication by checking raw tokens in widgets or individual route guards.

A route requiring authentication is accessible only when the application session boundary reports an authenticated state.

## 6. Authorization Boundary

Authentication establishes identity. Authorization determines whether an identity may perform or access a particular operation.

The Flutter router may prevent obviously inaccessible feature surfaces, but it is never the authoritative authorization mechanism.

For consequential operations:

```text
Client Navigation Guard
        │
        ▼
Backend Authorization
        │
        ▼
Authoritative Decision
```

A hidden or unreachable client route must never be treated as proof that an operation is secure.

Backend authorization remains authoritative under ADR-006 and the enterprise security architecture.

## 7. Feature Route Ownership

Each feature owns its internal navigation.

For example:

```text
Shopping Feature
├── Product Search
├── Product Results
├── Product Detail
└── Discovery Surface
```

The application shell references the feature entry point rather than reaching into internal widgets.

This prevents the root router from becoming a catalogue of feature implementation details.

A feature may therefore evolve internally without requiring unrelated application-shell changes.

## 8. Navigation State vs Feature State

Navigation state and feature state are distinct.

Navigation state answers:

> Where is the user?

Feature state answers:

> What is happening within that feature?

For example:

```text
Route: /checkout/review

Feature State:
  CheckoutSession = awaitingConfirmation
  Basket = loaded
  Pricing = confirmed
```

Navigating away from a screen must not automatically destroy consequential feature state unless the feature explicitly defines cancellation semantics.

The router therefore does not own checkout, payment, Walk Mode, or AI conversation state.

## 9. Route Parameters

Route parameters identify navigation targets; they do not carry authoritative domain state.

Examples:

```text
/products/{productId}
/orders/{orderId}
/walk/{sessionId}
```

A route parameter must be validated and resolved through the appropriate feature/application contract.

The client must not assume that possession of an identifier implies access to the underlying resource.

## 10. Deep Linking

Deep links are treated as navigation intents.

```text
External Intent
      │
      ▼
Deep-Link Resolver
      │
      ├── Session Check
      ├── Route Validation
      └── Feature Resolution
              │
              ▼
        Application Router
```

Examples include:

- product links;
- order links;
- notification links;
- household invitations;
- delivery tracking links;
- Walk Mode entry links where explicitly supported.

Deep links must converge on the same application routes used by ordinary navigation.

No deep-link path may create a privileged alternative to normal application behaviour.

## 11. Notification-Driven Navigation

Notifications may request navigation into a relevant feature, but notification handling must not directly manipulate feature internals.

```text
Notification
    ↓
Notification Intent
    ↓
Navigation Resolver
    ↓
Application Router
    ↓
Feature Entry Point
```

Examples:

- order status update → Order Detail;
- delivery update → Delivery surface;
- household event → Household surface;
- AI action awaiting approval → Approval surface;
- promotion or recommendation → relevant discovery surface.

The notification payload is an untrusted navigation input and must be validated before use.

## 12. Modal and Overlay Navigation

Not every interaction requires a full route.

The client distinguishes:

- route navigation;
- modal presentation;
- bottom sheet presentation;
- dialog presentation;
- transient notification/banner presentation.

Use a modal or sheet when the interaction is contextual and temporary.

Use a route when the interaction represents a meaningful application location or needs independent restoration/deep-link semantics.

Consequential approval actions must use explicit, recoverable surfaces rather than transient UI that can disappear without clear state handling.

## 13. Navigation Stack Semantics

Navigation stacks must preserve predictable back behaviour.

Rules:

- Back navigation must not silently commit or cancel consequential operations.
- A checkout flow must explicitly define whether leaving it preserves, pauses, or cancels the session.
- Leaving Walk Mode must trigger the session's explicit pause/exit semantics.
- Authentication transitions must clear protected navigation state where required.
- Sign-out must not leave protected screens reachable through stale navigation history.

The router must cooperate with feature lifecycle contracts rather than inventing them.

## 14. Checkout Navigation

Checkout is a bounded process and receives special treatment.

```text
Basket
  │
  ▼
Checkout Review
  │
  ├── Back → Basket
  │
  ▼
Confirmation
  │
  ├── Cancel → Defined checkout cancellation path
  │
  ▼
Processing
  │
  ▼
Result
  ├── Success → Order
  └── Failure → Recovery / Basket
```

The route hierarchy must not imply that payment succeeded merely because the user reached a confirmation screen.

Server-authoritative checkout and payment state remains the source of truth.

## 15. Walk Mode Navigation

Walk Mode is a bounded application surface with its own process lifecycle.

It supports the established three modes:

- Manual;
- AI Assisted;
- Autopilot.

Conceptually:

```text
Shopping / Basket
       │
       ▼
Walk Mode Setup
       │
       ▼
Active Walk Mode Session
       │
       ├── Manual
       ├── AI Assisted
       └── Autopilot
              │
              ├── User Takeover
              ├── Pause
              ├── Exit
              └── Completion
```

Navigation only presents and transitions the session surface.

It does not determine product availability, pricing, inventory authority, autonomous purchasing authority, or enterprise decisions.

User takeover must always be available according to the Walk Mode architecture and authorization policy.

## 16. AI Navigation Intents

AI may propose navigation, but navigation authority must remain bounded.

For example:

```text
AI proposes → Open Basket
AI proposes → View Product
AI proposes → Start Walk Mode
AI proposes → Review Checkout
```

A proposal is not an execution.

For actions requiring explicit human approval:

```text
AI Proposal
    ↓
Approval Surface
    ↓
User Decision
    ↓
Use Case
    ↓
Backend Authority
```

The client must not allow an AI response to directly invoke privileged navigation or consequential actions merely because the response contains a route-like instruction.

## 17. Offline and Limited Connectivity

The navigation architecture must remain usable under intermittent connectivity.

The application distinguishes:

- online and server-confirmed state;
- offline cached state;
- pending local operation;
- synchronisation in progress;
- synchronisation failure;
- action requiring renewed connectivity.

Offline navigation may open cached feature surfaces, but the UI must clearly distinguish cached information from confirmed server state.

Operations that require authoritative backend confirmation must not be represented as completed while offline.

## 18. Error and Recovery Navigation

Navigation errors are classified rather than treated as generic failures.

At minimum:

```text
Authentication Failure
Authorization Failure
Not Found
Conflict / Stale State
Connectivity Failure
Timeout
Server Failure
Cancellation
Unsupported Route
```

Recovery behaviour belongs to the application or feature responsible for the failure.

Examples:

- expired session → authentication;
- missing product → discovery/search;
- stale checkout → checkout recovery;
- connectivity failure → retry/offline surface;
- unauthorized order → safe error surface without revealing protected information.

## 19. Restoration and Lifecycle

The application must support appropriate restoration after:

- process termination;
- backgrounding;
- device rotation/configuration changes where applicable;
- connectivity loss;
- authentication expiry;
- interrupted bounded workflows.

Restoration must be based on durable or explicitly restorable application/feature state rather than assumptions about a previous widget tree.

Sensitive transient state must not be persisted merely for navigation convenience.

## 20. Accessibility and Navigation

Navigation must remain usable through platform accessibility mechanisms.

Requirements include:

- logical focus order;
- semantic labels for navigation controls;
- accessible back/close actions;
- predictable focus after route transitions;
- no navigation action that depends solely on gesture or visual positioning;
- accessible error and recovery surfaces;
- accessible user takeover and pause controls in Walk Mode.

Accessibility is a property of the navigation architecture, not a final cosmetic pass.

## 21. Observability

Navigation lifecycle events may be emitted to the established observability architecture.

Useful events include:

- navigation requested;
- navigation resolved;
- navigation rejected;
- deep link received;
- notification intent resolved;
- route transition completed;
- bounded workflow entered;
- bounded workflow exited;
- navigation failure.

Telemetry must not record credentials, access tokens, payment secrets, or unnecessary sensitive household data.

Navigation telemetry must use the established correlation and privacy controls.

## 22. Testing Requirements

The navigation architecture must be testable independently of individual widget implementations.

### Unit tests

- route resolution;
- session-to-route decisions;
- deep-link parsing;
- notification intent resolution;
- authorization-aware navigation gating;
- invalid route handling.

### Integration tests

- authentication transitions;
- deep links into authenticated features;
- notification-driven navigation;
- offline/online transitions;
- restoration of bounded workflows.

### Widget tests

- shell rendering;
- navigation controls;
- modal/sheet presentation;
- loading/error states;
- accessibility-critical navigation interactions.

### End-to-end tests

At least the critical journeys should be exercised end-to-end:

```text
Sign In → Home → Search → Product → Basket → Checkout → Order
Notification → Order Detail
Home → Walk Mode → Takeover → Exit
```

No navigation test should rely on bypassing the application shell through internal widget construction.

## 23. Architectural Guardrails

The following are prohibited:

- API calls directly from the router.
- Business rules embedded in route guards.
- Raw access-token inspection in feature widgets.
- Deep links that bypass backend authorization.
- Notification handlers that directly mutate feature state.
- AI responses directly invoking privileged operations.
- Router-owned checkout, payment, or Walk Mode business state.
- Treating route reachability as proof of authorization.
- Treating cached state as server-confirmed state.
- Destroying consequential process state merely because a screen was popped.
- Feature internals exposed as global navigation contracts without justification.

## 25. Result

Phase 4.4 establishes a Flutter application shell and navigation architecture that is session-aware, feature-oriented, deep-linkable, notification-aware, connectivity-conscious, testable, and compatible with the platform's trust boundaries.

Navigation remains a composition mechanism rather than a second business layer.

The client can therefore grow into a large Flutter application without turning the root router into a monolithic source of business logic or allowing feature boundaries to collapse.
