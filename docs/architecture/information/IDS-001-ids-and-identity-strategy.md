# IDS-001 — Enterprise IDs & Identity Strategy

**Status:** Proposed
**Date:** 2026-08-23
**Decision Type:** Information Architecture

---

## 1. Purpose

This document defines the identifier strategy for Essentials Mart's enterprise information model.

Identifiers are treated as architectural contracts, not implementation details. They must remain stable across services, databases, events, APIs, read models, AI systems, integrations, and future physical database decomposition.

This strategy implements the data-ownership principles established by ADR-005 and provides the identifier foundation required before the enterprise database model is designed.

---

## 2. Core Decision

Essentials Mart will use **opaque, globally unique identifiers** for authoritative enterprise entities.

The default identifier representation will be:

```text
UUID
```

Identifiers will be generated by the owning domain/application boundary and persisted as immutable identifiers.

Database-generated sequential integers, business names, email addresses, phone numbers, SKUs, usernames, or other mutable business attributes will **not** serve as enterprise entity identity.

Where an external system requires its own identifier, that identifier will be stored as an explicit external reference and will not replace the Essentials Mart identifier.

---

## 3. Identifier Principles

### 3.1 Identity is immutable

Once an authoritative entity receives an ID, the ID must never change during that entity's lifecycle.

### 3.2 IDs are opaque

Consumers must not infer business meaning, ownership, creation time, location, pricing, or sequencing from an ID.

### 3.3 IDs are not business attributes

Business attributes may change while the entity ID remains stable.

For example:

```text
customer.id       → stable identity
customer.email    → mutable attribute
customer.phone    → mutable attribute
customer.name     → mutable attribute
```

### 3.4 IDs cross boundaries; ownership does not

A domain may reference another domain's entity by ID without becoming its owner.

```text
Order.customerId → Customer.id
Order.productId  → Product.id
Delivery.orderId → Order.id
```

The reference does not transfer ownership.

### 3.5 No ID reuse

An ID must never be reassigned to another entity after deletion, archival, or retirement.

---

## 4. Identifier Types

Essentials Mart will distinguish between several identifier categories.

| Identifier | Purpose | Example |
|---|---|---|
| Entity ID | Internal authoritative identity | `UUID` |
| Aggregate ID | Identity of an aggregate root | `UUID` |
| Domain reference ID | Reference to another domain's entity | `UUID` |
| External ID | Identifier assigned by an external system | provider-defined |
| Correlation ID | Connects related operations/events | `UUID` |
| Causation ID | Identifies the event/command that caused another action | `UUID` |
| Idempotency key | Prevents duplicate command processing | opaque unique value |
| Version | Represents entity/aggregate revision | integer/version token |

These identifiers have different semantics and must not be conflated.

---

## 5. Aggregate IDs

Every aggregate root will possess its own stable identifier.

For example:

```text
Cart.id
CheckoutSession.id
Order.id
PaymentTransaction.id
Refund.id
Product.id
InventoryItem.id
```

Child entities or value objects will only receive independent IDs where their identity has a genuine lifecycle outside the aggregate root.

For example, an `OrderItem` normally remains subordinate to `Order` and does not require an enterprise-wide identity.

This prevents artificial identity from weakening aggregate boundaries.

---

## 6. Cross-Domain References

Cross-domain relationships will use identifiers rather than embedded authoritative objects.

Preferred:

```text
Order
 ├── customerId
 ├── householdId
 └── storeId
```

Not preferred:

```text
Order
 └── Customer { ...full authoritative customer object... }
```

A domain may maintain an authorised snapshot or read model when required, but the owning domain remains authoritative for the referenced entity.

## 7. External Identifiers

External systems will never be permitted to redefine Essentials Mart entity identity.

For example:

```text
PaymentTransaction
 ├── id                    → Essentials Mart ID
 ├── provider              → PSP identity
 └── providerTransactionId → external reference
```

This allows a payment provider to change, while the enterprise payment transaction remains identifiable within Essentials Mart.

External identifiers must be scoped to their provider/system where collisions are possible.

---

## 8. Human-Friendly Identifiers

Some entities may require human-readable references for customer service, receipts, store operations, or communication.

Examples include:

```text
Order number
Receipt number
Store code
SKU
Promotion code
Delivery reference
```

These are **business identifiers**, not authoritative entity identity.

They may be searchable, formatted, regenerated under defined rules, or changed when business requirements require it without changing the underlying entity ID.

---

## 9. Privacy and Security

Opaque IDs reduce accidental information disclosure, but an ID alone is not a security boundary.

Authorization must always be enforced independently of possession of an identifier.

For example:

```text
GET /orders/{orderId}
        │
        ▼
Authorization
        │
        ▼
Owned-order query
        │
        ▼
Order
```

Identifiers appearing in URLs, logs, events, or client applications must therefore be treated as potentially observable information.

Sensitive personal information must not be encoded directly into identifiers.

---

## 10. Event and Messaging Identity

Distributed operations require identifiers beyond entity IDs.

Events should carry, where applicable:

```text
eventId
correlationId
causationId
aggregateId
aggregateType
aggregateVersion
```

These support:

- duplicate detection;
- tracing;
- causality analysis;
- auditability;
- replay analysis;
- idempotent consumers;
- AI decision traceability.

The event identifier identifies the event itself. It must not be confused with the aggregate identifier.

---

## 11. Idempotency

Commands that may be retried across unreliable networks or asynchronous integrations must support idempotency where duplicate execution could cause harm.

This is especially important for:

- payments;
- orders;
- refunds;
- inventory reservations;
- deliveries;
- notifications with financial or operational consequences;
- WhatsApp-triggered actions;
- AI-initiated enterprise actions.

An idempotency key identifies an attempted operation. It does not become the entity's permanent identity unless explicitly designed as such.

---

## 12. Versioning and Concurrency

Entity identity and entity version are separate concepts.

```text
Order.id       → who/what this order is
Order.version  → which revision of the order state this represents
```

Aggregate versions will support optimistic concurrency where required.

A stale write must be rejected rather than silently overwriting a newer authoritative state.

The precise persistence mechanism will be defined during database architecture.

---

## 13. AI Society and Intelligence Engines

AI agents and Intelligence Engines may reference enterprise entities by their authoritative IDs.

They must not invent alternate authoritative identities for enterprise entities.

For example:

```text
AI Recommendation
 ├── recommendationId
 ├── customerId
 ├── productId
 └── generatedByAgentId
```

The recommendation has its own identity, while `customerId` and `productId` reference authoritative entities owned elsewhere.

AI-generated identifiers must therefore be distinguishable from identifiers of the enterprise entities they reference.

AI systems must not use mutable natural-language labels as durable identity.

---

## 14. Offline and WhatsApp Considerations

Essentials Mart must operate across environments with intermittent connectivity.

Client applications and WhatsApp interactions may hold references to enterprise entities while offline or between sessions.

Therefore:

- clients must not depend on sequential database IDs;
- identifiers must remain valid after synchronization;
- commands may carry idempotency keys to prevent replayed actions;
- locally generated identifiers may be accepted where offline creation is required, subject to the final synchronization strategy;
- server authority remains responsible for validating ownership and state transitions.

The exact offline ID-generation protocol will be defined when the Flutter and synchronization architectures are implemented.

---

## 15. Database Implications

The physical database must preserve the logical identifier model.

At minimum, authoritative tables will have:

```text
id
```

as their immutable primary identity.

Foreign keys may reference IDs across logically related structures where the physical deployment model permits it, but such relationships must not be used to bypass domain ownership rules.

The database must not introduce an alternative identity model merely because a particular storage technology makes sequential IDs convenient.

---

## 16. Naming Convention

Identifier fields will use explicit names that communicate what entity they reference.

Preferred:

```text
customerId
householdId
productId
orderId
paymentTransactionId
refundId
storeId
agentId
```

Avoid ambiguous names such as:

```text
id2
reference
owner
entity
item
```

Where an object contains its own identity, `id` is acceptable.

Where it references another entity, the referenced entity type should be explicit.

---

## 17. Prohibited Patterns

The following patterns are prohibited as authoritative identity:

- email address;
- phone number;
- username;
- product name;
- SKU;
- database row position;
- auto-increment sequence exposed as enterprise identity;
- timestamp alone;
- mutable external reference;
- AI-generated natural-language label.

These values may still be useful as alternate keys or business identifiers.

| Field | Required |
|---|---|
| Entity name | Yes |
| Owning domain | Yes |

| ID type | Yes |
| External IDs | If applicable |

| Parent aggregate | If applicable |
| Lifecycle | Yes |
| Data classification | Yes |
| Cross-domain references | If applicable |

This catalogue becomes the authoritative reference for database design.

## 19. Consequences

### Positive

- Stable identity across services and database evolution.
- Clear distinction between identity and business attributes.
- Safer cross-domain references.
- Better event correlation and auditability.
- Supports offline and unreliable-network workflows.
- Prevents accidental coupling to database implementation details.
- Supports future physical database decomposition.
- Provides a consistent foundation for APIs, events, AI, and integrations.

### Trade-offs

- UUIDs consume more storage than compact sequential integers.
- Human-friendly references require a separate business identifier.
- Distributed systems require additional correlation and idempotency identifiers.
- Offline creation requires a carefully governed synchronization strategy.

These are accepted architectural costs in exchange for durable enterprise identity.

## 21. Final Decision

> **Essentials Mart will use immutable, opaque, globally unique identifiers as the authoritative identity of enterprise entities. Cross-domain references will use explicit entity IDs without transferring ownership. External and human-friendly identifiers will remain separate from authoritative identity, while correlation, causation, idempotency, and version identifiers will serve their own distinct purposes. This identifier model will remain independent of physical database implementation and will form the identity foundation for the enterprise information model.**

**IDS-001 remains authoritative unless superseded by a subsequent architecture decision.**
