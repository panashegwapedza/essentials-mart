# Phase 3.5 — Event Bus & Integration Architecture

## Status

Proposed — derived from the enterprise architecture, EDA, EIP, ADRs, Phase 2 information architecture, and Phase 3 service/API boundaries.

## 1. Purpose

This document defines how Essentials Mart services communicate through domain events, integration events, commands, and external-provider integrations.

The event architecture exists to preserve service autonomy, enable eventual consistency across bounded contexts, support auditability, and allow the AI Society and other consumers to react to authoritative business facts without coupling directly to operational databases.

## 2. Core Principles

1. Services own their data and publish facts about state changes they own.
2. Events are immutable facts, not commands disguised as notifications.
3. Event consumers must be idempotent.
4. Eventual consistency is explicit and must not be mistaken for transactional consistency.
5. No service may read another service's database directly.
6. Events must use the authoritative enterprise event vocabulary.
7. Event schemas are versioned contracts.
8. Every consequential event is traceable to its source service and correlation context.
9. External provider payloads are normalized at the integration boundary.
10. The event bus is infrastructure; domain ownership remains with the publishing service.

## 3. Communication Model

```text
                 ┌───────────────────────┐
                 │   Domain Service      │
                 │  owns state + rules   │
                 └───────────┬───────────┘
                             │
                      domain event
                             │
                             v
                    ┌─────────────────┐
                    │    Event Bus    │
                    └───────┬─────────┘
                            /|\
                           / | \
                          v  v  v
                     Service AI  Audit
                     Consumer Society Service
```

Synchronous APIs are used when the caller needs an immediate authoritative response. Events are used when other bounded contexts need to react to a fact without becoming part of the publisher's transaction.

## 4. Event Categories

### 4.1 Domain Events

A domain event represents a significant fact inside a bounded context.

Examples:

- CartItemAdded
- CheckoutInitiated
- CheckoutExpired
- OrderCreated
- OrderPaid
- PaymentFailed
- RefundCreated
- InventoryReserved
- InventoryReservationReleased
- DeliveryAssigned

The final names must follow the authoritative enterprise event vocabulary rather than being invented independently by individual services.

### 4.2 Integration Events

Integration events are the stable contracts published for consumption outside the originating bounded context.

A service may internally have richer domain events than it exposes externally. The integration layer may translate internal events into a deliberately smaller public event contract.

### 4.3 Commands

Commands express requested actions and have an intended recipient.

Examples:

- ReserveInventory
- InitiatePayment
- ReleaseInventoryReservation
- CreateRefund
- SendNotification

Commands must not be broadcast as if they were facts.

## 5. Event Envelope

Every integration event must carry a standard envelope containing sufficient metadata for tracing, routing, replay, and auditing.

Example:

```json
{
  "eventId": "evt_01...",
  "eventType": "OrderCreated",
  "eventVersion": 1,
  "occurredAt": "2026-08-23T20:00:00Z",
  "producer": "order-service",
  "aggregateType": "Order",
  "aggregateId": "ord_123",
  "correlationId": "cor_123",
  "causationId": "cmd_123",
  "tenantId": "tenant_123",
  "payload": {}
}
```

Sensitive data must not be placed in the envelope or payload merely for convenience. Events should carry identifiers and business facts necessary for consumers, while consumers retrieve additional authorized data through their proper interfaces when necessary.

## 6. Aggregate-to-Event Ownership

| Aggregate / Capability | Authoritative publisher |
|---|---|
| Cart | Cart Service |
| Checkout Session | Checkout Service |
| Order | Order Service |
| Payment Transaction | Payment Service |
| Refund | Refund Service |
| Inventory Reservation | Inventory Service |
| Fulfillment | Fulfillment Service |
| Delivery | Delivery Service |
| Household | Household Service |
| Notification | Notification Service |
| Risk decision | Risk/Fraud Service |
| AI execution | AI Orchestration Service |

A consumer may react to another service's event, but it cannot publish a replacement event claiming ownership of that aggregate's state.

## 7. Commerce Event Flow

The principal commerce workflow is asynchronous across service boundaries:

```text
Cart
 │
 │ CheckoutInitiated
 ▼
Checkout
 │
 ├──────────────► Inventory: reserve stock
 │
 ├──────────────► Pricing/Tax/other intelligence as required
 │
 ▼
Order
 │
 └──────────────► Payment
                    │
                    ├── PaymentSucceeded ──► Order
                    │                         │
                    │                         ├──► Fulfillment
                    │                         ├──► Notification
                    │                         └──► Audit
                    │
                    └── PaymentFailed ─────► Checkout/Order
                                               │
                                               └──► Inventory release
```

The exact orchestration pattern may evolve, but no cross-service database transaction is introduced merely to make the workflow appear synchronous.

## 8. Transactional Outbox

Services that persist business state and publish integration events must use a transactional outbox or an equivalent durable publication mechanism in production.

The fundamental sequence is:

```text
Business transaction
       |
       +--> Aggregate state change
       |
       +--> Outbox event record
       |
       v
Commit
       |
       v
Outbox publisher
       |
       v
Event bus
```

This prevents the failure mode where database state commits but event publication is lost.

Publishing directly to the bus before the business transaction commits must not be treated as an equivalent guarantee.

## 9. Delivery Semantics

The baseline event-bus contract is **at-least-once delivery**.

Therefore:

- duplicate delivery is expected;
- consumers must be idempotent;
- event handlers must persist processing state where required;
- retries must use bounded backoff and dead-letter handling;
- exactly-once business effects must be achieved through consumer-side transactional/idempotency design, not assumed from transport semantics.

## 10. Consumer Idempotency

A consumer must safely handle receiving the same event more than once.

Typical pattern:

```text
receive event
   |
   v
check eventId / business idempotency key
   |
   +---- already processed ---> acknowledge / no-op
   |
   v
perform business operation
   |
   v
record processed event
   |
   v
acknowledge
```

The implementation must avoid marking an event processed before the corresponding business effect is durably committed.

## 11. Ordering

Ordering is guaranteed only within the scope explicitly provided by the event infrastructure.

Consumers must not assume global ordering across all Essentials Mart events.

Where ordering matters, events should carry an aggregate identifier and sequence/version information, allowing consumers to detect stale or out-of-order messages.

## 12. Retries and Dead Letters

Transient processing failures must be retried automatically.

A failed event should move through controlled retry attempts before being placed in a dead-letter/quarantine mechanism.

Dead-letter processing must support:

- visibility;
- reason classification;
- replay after remediation;
- operator authorization;
- auditability;
- protection against infinite replay loops.

A dead-letter event must never simply disappear.

## 13. Event Schema Evolution

Event schemas are contracts.

Compatible changes should be additive where practical. Breaking changes require an explicit version transition.

Example:

```text
OrderCreated v1
OrderCreated v2
```

Consumers must be able to declare the versions they support during migration.

Removing or changing the meaning of an existing field requires deliberate compatibility management.

## 14. Eventual Consistency

Eventual consistency is expected between independent aggregates and services.

For example:

```text
PaymentSucceeded
       |
       v
Order status eventually becomes Paid
       |
       v
Fulfillment eventually receives work
       |
       v
Notification eventually informs customer
```

The user-facing application must expose meaningful intermediate states rather than pretending the entire workflow is one atomic transaction.

## 15. External Integrations

External systems are isolated behind integration adapters.

Examples include:

- payment service providers;
- delivery providers;
- WhatsApp providers;
- messaging providers;
- maps/location providers;
- identity providers.

The adapter translates external protocols into internal commands/events and prevents provider-specific contracts from becoming domain contracts.

## 16. Payment Integration

Payment provider webhooks are authoritative inputs into the Payment Service after provider signature/authentication and payload validation.

The flow is:

```text
PSP
 |
 | webhook
 v
Payment Integration Adapter
 |
 | normalized event
 v
Payment Service
 |
 +--> PaymentSucceeded / PaymentFailed
```

The Order Service must not communicate directly with a payment provider to determine financial truth.

## 17. Inventory Integration

Inventory reservations are modeled as explicit business state.

A checkout may request a reservation with a TTL. Inventory emits the authoritative reservation result.

Possible facts include:

- InventoryReservationRequested
- InventoryReserved
- InventoryReservationFailed
- InventoryReservationExpired
- InventoryReservationReleased

The exact authoritative vocabulary will be maintained centrally rather than duplicated across service documents.

## 18. AI Society Integration

The AI Society consumes events as signals about the living state of the platform.

Examples:

```text
OrderCreated
   ├── Household Agent
   ├── Recommendation Intelligence
   ├── Notification Agent
   └── Audit / Trust

InventoryChanged
   ├── Shopping Agent
   ├── Inventory Intelligence
   ├── Demand Forecasting
   └── Product Discovery

DeliveryDelayed
   ├── Delivery Coordination Agent
   ├── Customer Support Agent
   └── Notification Agent
```

AI consumers remain subject to authorization, capability limits, privacy controls, and human-approval requirements defined by the AI architecture.

## 19. Auditability

Consequential events must be traceable through:

- event ID;
- aggregate ID;
- producer;
- correlation ID;
- causation ID;
- timestamp;
- actor/principal where applicable;
- AI agent/capability where applicable.

Audit records are not replaced by event retention alone. The Audit Service maintains the authoritative audit representation required by the trust architecture.

## 20. Observability

Event processing must expose operational telemetry including:

- publish success/failure;
- consumer lag;
- processing latency;
- retry count;
- dead-letter count;
- duplicate rate;
- handler failures;
- correlation traces.

Events must be correlated with API requests, commands, database transactions, AI actions, and external-provider interactions where technically possible.

## 21. Security and Privacy

The event bus is a privileged internal infrastructure component.

Controls include:

- service identity;
- topic/stream authorization;
- encryption in transit and at rest;
- least-privilege consumer permissions;
- sensitive-data minimization;
- retention policies;
- audit logging;
- tenant isolation where applicable.

Events containing personal, household, financial, or location information require explicit classification and handling rules.

## 22. No Direct Database Integration

This is prohibited:

```text
Service A ──► Service B database
```

The required pattern is:

```text
Service A ──► Service B API / command / event
                         |
                         v
                  Service B database
```

This preserves ownership and prevents hidden coupling.

## 23. Event Replay

The platform must support controlled replay for recoverability and rebuilding authorized projections.

Replay must distinguish between:

- rebuilding a read model;
- reprocessing an operational event;
- reproducing an external side effect.

External side effects must not be blindly repeated during replay. Consumers must use idempotency and explicit replay policies to prevent duplicate payments, notifications, deliveries, or other irreversible actions.

## 24. Event Retention

Retention periods are determined by event classification, audit requirements, operational recovery needs, privacy obligations, and storage economics.

High-value financial/audit facts require stronger retention guarantees than ephemeral UI-oriented signals.

Retention and deletion policies must not undermine legally or architecturally required audit records.

## 25. Phase 3.5 Exit Criteria

Phase 3.5 is complete when:

- domain and integration event responsibilities are defined;
- commands are distinguished from events;
- the event envelope is defined;
- aggregate ownership is explicit;
- transactional outbox is established as the production publication pattern;
- at-least-once delivery and consumer idempotency are explicit;
- retry/dead-letter behavior is defined;
- event ordering assumptions are documented;
- schema evolution/versioning is defined;
- external integrations are isolated behind adapters;
- AI Society consumption follows the same event governance;
- audit and observability requirements are defined;
- replay and retention policies are established.
