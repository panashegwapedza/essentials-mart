# Phase 3.6 — AI Orchestration & Intelligence Engine Architecture

## Status

Proposed — derived from the enterprise architecture, EDA, EIP, ADRs, Phase 2 information architecture, and Phase 3 service and integration boundaries.

## 1. Purpose

This document defines how Essentials Mart coordinates AI agents, Intelligence Engines, tools, data access, permissions, decisions, and human oversight.

The objective is not to create a collection of independent AI features. Essentials Mart uses a governed **AI Society** in which specialised agents collaborate through explicit capabilities and orchestration while domain services remain the authoritative owners of business state.

## 2. Architectural Rule

AI does not become a second system of record.

```text
                  AI Society
                      │
          ┌───────────┴───────────┐
          │   AI Orchestrator     │
          └───────────┬───────────┘
                      │
          ┌───────────┴───────────┐
          │ Intelligence Engines  │
          └───────────┬───────────┘
                      │
             authorized tools
                      │
                      v
        Domain Services / Read Models
                      │
                      v
             Authoritative State
```

Agents reason over authorized information and request actions through governed interfaces. They do not bypass service boundaries or directly mutate domain databases.

## 3. AI Society

The AI Society is the coordinated population of specialised AI agents and supporting Intelligence Engines.

Representative agents include:

- Household Agent
- Shopping Agent
- Product Discovery Agent
- Recommendation Agent
- Inventory Agent
- Pricing Agent
- Customer Support Agent
- Delivery Coordination Agent
- Store Operations Agent
- Personalisation Agent
- Notification Agent
- Demand Forecasting Agent
- Fraud and Risk Agent
- Enterprise Intelligence Agent
- Walk Mode Agent

The list is extensible. New agents must have a clearly defined purpose, authority, data access, and owner.

## 4. Agents vs Intelligence Engines

### Agents

Agents are goal-oriented actors that interpret context, plan work, communicate with users or other agents, and invoke authorized capabilities.

### Intelligence Engines

Intelligence Engines provide specialised decision or inference capabilities that can be reused by multiple agents.

Examples:

- Recommendation Engine
- Demand Forecasting Engine
- Pricing Intelligence Engine
- Inventory Optimization Engine
- Fraud/Risk Engine
- Personalisation Engine
- Product Discovery Engine
- Route Optimization Engine

An agent may ask an engine for an analysis, but an engine does not independently acquire unrestricted authority to execute business actions.

## 5. Orchestrator Responsibilities

The AI Orchestrator is responsible for coordinating AI work.

It must:

- identify the appropriate agent/capability;
- construct authorized context;
- enforce capability permissions;
- coordinate multi-agent work;
- manage tool calls;
- enforce budgets and timeouts;
- maintain correlation and trace information;
- apply human-approval requirements;
- handle failures and retries;
- prevent uncontrolled agent recursion;
- record consequential AI decisions.

The orchestrator must not replace domain services as the owner of business rules or state.

## 7. Capability-Based Authority

AI authority is granted through explicit capabilities rather than through general backend credentials.

Examples:

- `basket.read`
- `basket.modify`
- `order.read`
- `order.cancel`
- `inventory.read`
- `delivery.coordinate`
- `notification.send`
- `household.read`
- `payment.status.read`

Capabilities must be scoped by tenant, user, household, domain, action, and other applicable policy dimensions.

An agent possessing `order.read` does not automatically possess `order.cancel`.

## 8. Read vs Write Authority

AI read access may be broad enough to build useful context, subject to privacy and least-privilege rules.

AI write access must be narrowly scoped and explicitly governed.

```text
Read data
   ↓
Reason
   ↓
Propose action
   ↓
Policy / permission evaluation
   ↓
Human approval where required
   ↓
Authorized domain command
```

Direct database writes by agents are prohibited.

## 9. Intelligence Engine Contract

An Intelligence Engine should behave as a bounded analytical capability.

Conceptually:

```text
Input Context
     |
     v
Intelligence Engine
     |
     +--> result
     +--> confidence
     +--> model/version metadata
     +--> explanation/decision factors where available
```

Engine output is not automatically an instruction to execute an action.

For consequential decisions, the output must include sufficient metadata to support audit, evaluation, and reproducibility within the limits of the underlying model.

## 10. Determinism and Reproducibility

AI outputs are not assumed to be deterministic.

For consequential workflows the platform records, where applicable:

- model/provider;
- model version;
- prompt or policy version reference;
- engine version;
- relevant input/context references;
- tool calls;
- decision/result;
- confidence or uncertainty indicators;
- policy evaluation;
- human approval;
- timestamp;
- correlation and causation IDs.

Sensitive prompts and raw personal data must be handled according to the platform's privacy and retention policies.

## 11. Multi-Agent Coordination

Agents must collaborate through explicit orchestration rather than uncontrolled agent-to-agent recursion.

```text
Orchestrator
   |
   +--> Shopping Agent
   |
   +--> Inventory Intelligence
   |
   +--> Recommendation Agent
   |
   +--> Household Agent
```

The orchestrator maintains the task context and determines which agent may act next.

An agent may request another capability through the orchestrator, but cannot silently grant itself additional authority.

## 12. Conflict Resolution

The AI Society must not present contradictory recommendations simply because multiple agents independently reasoned about the same question.

When multiple agents produce competing outputs:

1. identify the applicable domain authority;
2. evaluate policy constraints;
3. compare evidence and confidence;
4. apply deterministic business rules where available;
5. escalate to a human when the consequence or uncertainty requires it;
6. record the resolution.

Domain rules always outrank an AI preference.

## 13. Human-in-the-Loop

Human approval is required for actions classified as high impact, irreversible, financially consequential, privacy-sensitive, or otherwise restricted by policy.

Examples may include:

- high-value purchases;
- refunds above configured thresholds;
- sensitive household changes;
- destructive account operations;
- exceptional delivery actions;
- high-risk fraud decisions.

The policy engine determines whether approval is required; an agent cannot waive its own approval requirement.

## 14. Tool Execution

AI tools are wrappers around authorized platform capabilities.

A tool must define:

- capability required;
- input schema;
- output schema;
- authorization rules;
- side-effect classification;
- idempotency requirements;
- audit requirements.

Examples:

```text
getBasket()
addBasketItem()
removeBasketItem()
getOrder()
requestInventoryHold()
sendNotification()
getDeliveryStatus()
```

Tools must call the appropriate domain service/API rather than accessing persistence directly.

## 15. Side-Effect Classification

Every AI-invoked tool must be classified as one of:

- **Read-only** — no state change.
- **Reversible write** — state can safely be undone.
- **Consequential write** — meaningful business effect.
- **Irreversible/high-impact** — requires stronger controls.

The classification determines the required authorization and human-approval policy.

## 16. Event-Driven AI Activation

The AI Society may be activated by enterprise events.

Examples:

```text
InventoryChanged
      |
      v
Inventory Intelligence
      |
      v
Demand Forecasting
      |
      v
Store Operations Agent
```

```text
DeliveryDelayed
      |
      v
Delivery Coordination Agent
      |
      +--> Customer Support Agent
      +--> Notification Agent
```

Event-driven activation must remain bounded and idempotent. An event must not create an uncontrolled feedback loop of AI actions and new events.

## 17. AI and Domain Ownership

The relationship is:

```text
AI Society = intelligence + coordination
Domain Services = business authority + state
Database = persistence
Event Bus = communication
```

AI may recommend that an order be cancelled. Only the authorized Order Service command can actually change the order.

AI may recommend an inventory adjustment. Only the Inventory domain can commit the inventory change.

This separation is fundamental to trust and auditability.

## 18. Context Construction

Agents should receive the minimum context necessary to perform their task.

Context may come from:

- authorized domain APIs;
- read models;
- event streams;
- user-provided information;
- household context;
- relevant Intelligence Engine outputs.

The orchestrator must avoid indiscriminately sending entire customer records to models.

## 19. Memory

AI memory is divided conceptually into:

- **Working context** — information needed for the current task.
- **Session context** — information retained during an interaction.
- **User/household preferences** — durable preferences explicitly permitted for retention.
- **Enterprise knowledge** — governed knowledge sources.
- **Operational state** — remains in domain services and is not replaced by AI memory.

AI memory must never become an ungoverned shadow database for business state.

## 20. Model and Provider Abstraction

The architecture must not make the business domain dependent on a single AI model provider.

```text
AI Orchestrator
       |
   Model Gateway
   /     |      \
Model A Model B  Model C
```

The gateway may handle:

- provider selection;
- fallback;
- model routing;
- cost controls;
- latency policies;
- safety policies;
- observability.

Provider-specific APIs remain behind the integration boundary.

## 21. Failure Handling

AI failures must fail safely.

Possible failures include:

- model timeout;
- provider outage;
- malformed model output;
- tool failure;
- policy denial;
- insufficient permissions;
- low confidence;
- context retrieval failure;
- orchestration loop.

The system must have deterministic fallback behavior where practical, including non-AI workflows for critical commerce operations.

AI availability must not become a prerequisite for basic transaction integrity.

## 22. Cost and Resource Governance

AI execution is subject to budgets and quotas.

Controls may include:

- per-request token budget;
- per-user/household quota;
- per-agent budget;
- model tier selection;
- execution timeout;
- maximum tool calls;
- maximum orchestration depth;
- rate limits.

An agent must not recursively consume unbounded resources.

## 23. Security

AI execution must be treated as privileged computation.

Required controls include:

- authenticated service identity;
- capability-based authorization;
- tenant isolation;
- secret isolation;
- prompt/input validation;
- output validation;
- tool allowlists;
- audit logging;
- sensitive-data minimization;
- model/provider policy controls.

Untrusted model output must never be interpreted as trusted executable instructions without validation.

## 24. Prompt Injection and Untrusted Data

External content, product descriptions, reviews, messages, documents, web content, and user-generated data must be treated as untrusted input.

The orchestrator must separate:

- system/policy instructions;
- trusted application context;
- user intent;
- untrusted retrieved content;
- tool results.

An AI agent must not gain authority merely because untrusted content instructs it to perform an action.

## 25. AI Decision Audit

Consequential AI decisions must produce an auditable decision record containing, as appropriate:

- actor/agent;
- capability;
- triggering event/request;
- input references;
- engine/model versions;
- output/result;
- confidence/uncertainty;
- policy decision;
- human approval;
- action executed;
- resulting event IDs.

This integrates with the existing Observability, Auditability & Trust architecture.

## 26. Walk Mode Integration

Walk Mode is an AI Society consumer and orchestrated capability, not a separate AI universe.

The Walk Mode Agent may:

- interpret the shopping goal;
- plan routes;
- recognize relevant products;
- surface alternatives;
- respond conversationally;
- detect unavailable products;
- request basket changes;
- reroute dynamically.

However, basket changes and purchases still execute through the authoritative Commerce APIs and domain services.

## 27. WhatsApp Integration

WhatsApp is a communication channel into the AI Society, not a separate business backend.

```text
WhatsApp
   |
Channel Adapter
   |
AI Orchestrator
   |
Authorized Agent
   |
Domain API / Command
```

The same authorization, audit, privacy, and capability policies apply whether a request originates from the mobile application, WhatsApp, or another supported channel.

## 28. Evaluation and Quality Gates

Intelligence Engines and agents must be evaluated independently from ordinary unit tests.

Evaluation should cover:

- accuracy;
- groundedness;
- policy compliance;
- tool-use correctness;
- refusal behavior;
- adversarial inputs;
- latency;
- cost;
- regression against approved evaluation sets.

No AI capability should be promoted to production solely because a small collection of example conversations appears successful.

## 29. Versioning

The following may require independent versioning:

- agent behavior/configuration;
- Intelligence Engine implementation;
- model/provider;
- prompt/policy templates;
- tool contracts;
- evaluation datasets.

Consequential decisions must be attributable to the versions used at execution time.

## 30. Phase 3.6 Exit Criteria

Phase 3.6 is complete when:

- AI Society responsibilities are defined;
- agent and Intelligence Engine boundaries are explicit;
- orchestration is centralized and governed;
- capabilities and authority are explicit;
- tool execution is bounded;
- human-in-the-loop controls are defined;
- AI/domain ownership boundaries are enforced;
- event-driven activation is governed;
- model/provider abstraction is established;
- failure and fallback behavior is defined;
- cost/resource governance is defined;
- security and prompt-injection controls are defined;
- AI decision auditability is defined;
- Walk Mode and WhatsApp integrate through the same governed architecture;
- evaluation and versioning requirements are defined.
