# Essentials Mart — Backend Testing & Verification Architecture

**Phase:** 3.14 — Backend Architecture  
**Status:** Proposed  
**Date:** 2026-08-23  
**Authority:** ADR-016, ADR-004, ADR-003, ADR-015, ADR-018

## 1. Purpose

This document defines the verification architecture for the Essentials Mart backend.

Testing is treated as an architectural control rather than only a development activity. The verification system must demonstrate that backend implementations preserve domain ownership, API contracts, security boundaries, event semantics, persistence invariants, AI governance, observability and operational resilience.

The objective is not maximum test count. The objective is trustworthy evidence that the implemented system behaves according to its authoritative architecture.

## 2. Architectural Principles

1. **Architecture is executable** — material architectural invariants must have corresponding verification where practical.
2. **Test behaviour, not implementation trivia** — tests should verify contracts and outcomes rather than private implementation details.
3. **Production boundaries are explicit** — development adapters must not be mistaken for production guarantees.
4. **Failure paths are first-class** — invalid input, dependency failure, timeout, retry, conflict and recovery paths require verification.
5. **Security properties are tested directly** — authentication, authorisation, ownership and enumeration resistance must not rely on incidental coverage.
6. **Contracts are verified at boundaries** — API, event and integration contracts must be tested independently of internal implementation.
7. **Determinism is preferred where the architecture requires it** — tests must avoid uncontrolled time, randomness and shared global state.
8. **Tests must be isolated** — one test must not depend on mutation performed by another test.
9. **Evidence must be reproducible** — a failing verification must provide enough context to reproduce and diagnose the failure.
10. **False confidence is worse than missing coverage** — tests must never claim guarantees that the underlying adapter or architecture does not provide.

## 3. Verification Layers

Essentials Mart uses multiple complementary verification layers:

| Layer | Primary purpose |
|---|---|
| Static analysis | Type and structural correctness |
| Unit tests | Domain rules and deterministic components |
| Application tests | Use-case behaviour and orchestration |
| API/contract tests | External HTTP contract correctness |
| Integration tests | Real boundary interactions |
| Event tests | Publication, consumption and schema behaviour |
| Security tests | Trust and access-control invariants |
| Persistence tests | Transactional and ownership guarantees |
| End-to-end tests | Critical user/business journeys |
| Resilience tests | Failure, retry and degradation behaviour |
| Performance tests | Capacity and latency characteristics |
| Operational verification | Observability, health and deployment behaviour |

No single layer substitutes for the others.

## 4. Test Pyramid and Boundary Strategy

The backend should maintain a broad base of fast deterministic tests and a smaller number of expensive environment-dependent tests.

```text
                 End-to-End
              /--------------\
             /  Resilience /  \
            /  Performance     \
           / Integration/API    \
          /---------------------\
         / Application / Domain  \
        /-------------------------\
       /      Unit / Pure Logic    \
      /-----------------------------\
```

The exact distribution is implementation-dependent. The architectural requirement is that important behaviour is verified at the lowest meaningful boundary and then selectively verified again at higher boundaries.

## 5. Unit Verification

Pure domain logic must be independently testable without HTTP, databases, queues or external providers.

Unit tests should cover:

- invariants;
- state transitions;
- value calculations;
- validation rules;
- pricing and currency rules;
- ownership rules;
- deterministic transformations;
- error classifications; and
- edge conditions.

Unit tests must not require mutable process-wide configuration merely to construct normal test fixtures.

## 6. Application-Service Verification

Application services must be tested for orchestration and boundary behaviour.

Verification should include:

- correct repository calls;
- correct domain operation selection;
- authorization enforcement;
- correct propagation of stable error codes;
- transaction/command sequencing where applicable;
- event publication requests;
- idempotency behaviour; and
- failure propagation.

Tests must distinguish application responsibility from infrastructure responsibility.

## 7. API and Contract Verification

Every externally exposed API contract must have verification for:

- supported methods;
- path and parameter validation;
- authentication requirements;
- authorization and ownership enforcement;
- request validation;
- response shape;
- status codes;
- stable machine-readable error codes;
- content types;
- payload-size limits;
- malformed input; and
- unsupported operations.

HTTP status mapping must depend on stable classifications rather than human-readable error-message text.

API tests must also verify that internal domain-only fields do not leak through public DTOs.

## 8. Authentication and Authorization Verification

Security tests must explicitly verify fail-closed behaviour.

At minimum:

- missing credentials are rejected;
- malformed credentials are rejected;
- unauthorized principals cannot access protected operations;
- authenticated users cannot access another customer's resources;
- privileged operations require appropriate authority;
- development authentication cannot activate accidentally in production configuration; and
- authentication configuration errors fail safely.

Negative authorization tests are mandatory for security-sensitive resources.

## 9. Ownership and Enumeration Resistance

Resource ownership must be tested at the repository/application boundary, not merely after a broad lookup.

For customer-owned resources, verification should demonstrate that a request scoped to customer A cannot retrieve or infer customer B's resource through:

- direct lookup;
- alternate endpoints;
- identifiers;
- error differences; or
- pagination/filtering paths.

Repository contracts should support scoped queries where ownership is part of the lookup condition.

## 10. Persistence Verification

Production persistence implementations must be tested against their actual transactional semantics.

Verification should cover:

- transaction boundaries;
- uniqueness constraints;
- foreign-key relationships;
- optimistic/pessimistic concurrency controls where applicable;
- idempotency keys;
- rollback behaviour;
- partial failure;
- isolation expectations; and
- durable state after process restart.

In-memory adapters may verify application behaviour but must never be used as proof of production database atomicity or isolation.

## 11. Event and Message Verification

Event verification must cover:

- authoritative event type and version;
- schema validation;
- required metadata;
- correlation and causation identifiers;
- producer ownership;
- consumer handling;
- duplicate delivery;
- retry behaviour;
- dead-letter behaviour; and
- compatibility across supported schema versions.

Consumers must be tested for idempotent handling wherever duplicate delivery is possible.

## 12. External Integration Verification

Third-party providers must be tested through explicit adapter contracts.

Tests should cover:

- successful provider response;
- provider rejection;
- timeout;
- network failure;
- malformed provider response;
- duplicate callback/webhook;
- delayed callback;
- retry behaviour;
- circuit/degradation behaviour; and
- provider reference correlation.

Provider sandbox tests and production verification must remain distinct.

## 13. Concurrency Verification

Concurrency tests must only claim properties actually guaranteed by the implementation under test.

For example, an in-memory adapter that lacks transactional isolation must not have a test asserting exactly-one-success semantics merely because production will eventually require it.

Where concurrency guarantees are architectural requirements, verification must execute against an implementation capable of providing those guarantees, normally through the production persistence or transaction mechanism.

Development tests may instead verify currently valid properties such as:

- server responsiveness;
- response structural validity;
- absence of corrupted state;
- deterministic sequential behaviour; and
- explicit acknowledgement that atomicity is not claimed.

## 14. Idempotency Verification

Idempotent operations must be tested with repeated and concurrent submissions.

Verification should demonstrate that:

- the same idempotency key does not create duplicate business effects;
- equivalent retries return a consistent result;
- conflicting reuse of an idempotency key is rejected;
- persisted idempotency state survives the relevant failure boundary; and
- external provider retries do not create duplicate financial or fulfilment effects.

## 15. State-Machine Verification

Important lifecycle entities must have explicit transition tests.

Examples include:

- Checkout Session;
- Order;
- Payment Transaction;
- Refund;
- Inventory Hold;
- Fulfilment; and
- Delivery.

Verification should cover valid transitions, invalid transitions, terminal states, repeated events and recovery paths.

## 16. AI Society Verification

AI-related backend behaviour must be tested for both capability and authority.

Verification should establish that:

- an agent cannot invoke capabilities outside its declared authority;
- policy constraints are enforced independently of model output;
- human approval gates cannot be bypassed;
- AI actions are attributable;
- prohibited actions are rejected deterministically;
- agent-to-agent interactions preserve identity and correlation context; and
- AI recommendations cannot silently become authoritative domain state without the required command/approval path.

Tests must not treat successful model output as proof of authorization.

## 17. Observability Verification

Observability is itself testable.

Critical tests should verify the presence and propagation of:

- trace identifiers;
- request identifiers;
- correlation identifiers;
- causation identifiers;
- actor context where required;
- stable error codes;
- audit records for material actions; and
- dependency outcome telemetry.

Tests should also verify that sensitive credentials and prohibited data are not emitted into logs or telemetry.

## 18. Property and Invariant Testing

Where useful, property-based testing should verify broad invariant spaces rather than isolated examples.

Candidate invariants include:

- monetary totals never use mixed currencies;
- quantities remain valid integers;
- owned resources cannot cross customer boundaries;
- terminal lifecycle states cannot transition illegally;
- public DTOs contain only approved fields;
- event identifiers remain unique within their defined scope; and
- retries do not multiply idempotent business effects.

Property testing must remain deterministic and reproducible through controlled seeds when randomness is involved.

## 19. Test Data and Fixtures

Test data must be explicit, isolated and purpose-built.

Rules:

- fixtures must be clearly identified;
- production data must never be copied into tests without governed anonymisation;
- tests must not mutate global environment state unnecessarily;
- fixture configuration should be passed explicitly where possible;
- sensitive values must use safe synthetic data; and
- test data must not accidentally become a production default.

Development fixture adapters must remain clearly separated from production repositories.

## 20. Time, Randomness and External State

Tests must avoid hidden dependencies on wall-clock time, randomness and external services.

Where behaviour depends on time, use an injectable clock or controlled time source.

Where identifiers or randomness are generated, tests should use deterministic substitutes when verification requires repeatability.

External network access must not be required for ordinary unit and application test execution.

## 21. Test Isolation and Parallelism

Tests must be safe to execute independently and, where supported, in parallel.

Tests must not rely on:

- execution order;
- mutable module-level state;
- uncontrolled `process.env` mutation;
- shared databases without isolation;
- global singleton state; or
- residual temporary files.

When shared infrastructure is required, its lifecycle and isolation strategy must be explicit.

## 22. Build and Test Discovery

The repository's test command must use deterministic test discovery supported by the runtime rather than shell-specific recursive glob behaviour.

The standard backend test flow should:

1. compile the TypeScript source;
2. discover all compiled tests recursively;
3. execute them under the supported Node test runner;
4. fail on test or compilation errors; and
5. produce sufficient output for diagnosis.

Cross-platform development commands must not depend on POSIX-only environment-variable syntax.

## 23. Coverage and Quality Gates

Coverage is a signal, not the sole quality metric.

Quality gates should prioritize:

- critical domain invariants;
- security boundaries;
- financial correctness;
- ownership enforcement;
- event contracts;
- idempotency;
- AI authority controls;
- persistence correctness; and
- critical operational paths.

A high aggregate line-coverage percentage does not compensate for missing verification of a critical architectural invariant.

## 24. End-to-End Critical Journeys

A controlled end-to-end suite should verify the highest-value journeys, including where applicable:

1. authentication;
2. product discovery;
3. basket creation and modification;
4. checkout initiation;
5. inventory reservation;
6. payment authorization;
7. order creation;
8. fulfilment progression;
9. delivery progression;
10. notification delivery;
11. refund processing; and
12. AI-assisted actions requiring governed authority.

The suite should remain intentionally smaller than unit/application verification and should focus on cross-boundary confidence.

## 25. Resilience and Failure Verification

Critical services must be tested under controlled failures.

Scenarios include:

- dependency timeout;
- dependency outage;
- queue backlog;
- duplicate events;
- delayed events;
- database interruption;
- partial service failure;
- process restart;
- retry exhaustion; and
- degraded-mode operation.

The purpose is to verify that failures preserve consistency and remain observable rather than simply proving that the service can fail.

## 26. Performance Verification

Performance testing must be based on defined service-level objectives and realistic workloads.

It should evaluate:

- throughput;
- latency distribution;
- concurrency;
- queue processing rate;
- database behaviour;
- external dependency impact; and
- resource saturation.

Performance tests must not be used to establish correctness properties that belong to functional or transactional verification.

## 27. Security and Abuse Verification

Security verification should include:

- authentication bypass attempts;
- authorization bypass attempts;
- resource enumeration;
- malformed payloads;
- oversized payloads;
- rate-limit behaviour where implemented;
- injection resistance;
- secret leakage checks;
- unsafe error disclosure; and
- abuse of privileged or AI capabilities.

Security tests must be repeatable and must not require production customer data.

## 28. CI/CD Verification Gates

The backend delivery pipeline should enforce, at minimum:

1. formatting/lint checks where adopted;
2. TypeScript compilation;
3. unit and application tests;
4. API/contract tests;
5. security-focused tests;
6. integration tests appropriate to the deployment stage;
7. artifact/build verification; and
8. deployment smoke tests where applicable.

Production deployment must not be considered successful merely because compilation passed.

## 29. Verification Evidence

Each significant verification stage should produce machine-readable or otherwise reviewable evidence.

Evidence should identify:

- commit/version under test;
- environment;
- test suite/version;
- execution timestamp;
- pass/fail outcome;
- relevant configuration;
- failure diagnostics; and
- artifact or report references where applicable.

Evidence must not contain unnecessary secrets or sensitive customer data.

## 30. Architectural Invariants

The following are non-negotiable:

1. Tests must not claim guarantees that an implementation does not provide.
2. Security and ownership boundaries must have explicit negative tests.
3. Financial and lifecycle invariants must be directly verified.
4. Stable machine-readable error codes must be tested independently of message wording.
5. Public DTOs must not expose unapproved domain fields.
6. Event consumers must account for duplicate delivery where applicable.
7. Idempotent operations must be verified under retry conditions.
8. AI capability and authority must be tested as separate concerns.
9. Production persistence guarantees must be verified against production-class persistence mechanisms.
10. Test execution must be isolated, reproducible and cross-platform.

## 33. Acceptance Criteria

Phase 3.14 is architecturally satisfied when:

- critical domain invariants have direct verification;
- API and event contracts are tested;
- security and ownership boundaries have negative tests;
- production persistence guarantees are verified at the appropriate integration layer;
- idempotency and lifecycle transitions are verified;
- AI capability and authority controls are independently tested;
- observability and audit evidence are verified;
- failure and resilience paths are tested at the appropriate level;
- CI/CD gates enforce the required verification layers; and
- verification evidence is reproducible and attributable to a specific build/version.

## 34. Decision

Essentials Mart will treat backend verification as an architectural capability spanning static analysis, unit tests, application tests, API and event contracts, integration testing, security verification, persistence verification, AI governance testing, resilience testing, performance testing and operational smoke tests.

The system will favour **truthful, boundary-aware and reproducible verification** over superficial coverage. Development adapters may demonstrate application behaviour, but production guarantees must ultimately be verified against production-class infrastructure and integration boundaries.
