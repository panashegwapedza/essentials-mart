# Phase 3.2 — Physical Database Schema Specification

## Status
Defined — Phase 3.2

## Purpose

This document translates the frozen Phase 2 information architecture and the Phase 3.1 logical database architecture into a physical database specification.

It defines the required schema boundaries, table ownership, keys, constraints, indexes, persistence rules and Row Level Security boundaries for the first production relational implementation.

This document is a schema specification, not a migration. Physical migrations must implement this specification without changing domain ownership or aggregate boundaries.

## 1. Physical Persistence Strategy

The relational database is organised around domain ownership rather than around one enterprise-wide transactional schema.

Logical domain schemas are used to make ownership visible in the database:

```text
identity
household
catalog
store
inventory
commerce
payments
refunds
fulfilment
delivery
notifications
ai_society
risk
store_operations
intelligence
platform
```

A schema represents a persistence ownership boundary. It does not mean that every domain must immediately become a separately deployed database service.

The initial implementation may use one PostgreSQL/Supabase database while preserving these ownership boundaries at the schema, role, API and service layers. Physical database separation can occur later without changing the logical model.

## 3. Common Column Conventions

Authoritative tables should use the following conventions unless an entity-specific rule requires otherwise.

### Identity

```text
id UUID PRIMARY KEY
```

IDs are opaque, immutable and generated independently of business names.

External identifiers must use separate columns, for example:

```text
external_id
provider_customer_id
psp_transaction_id
supplier_id
```

They must never replace the internal entity ID.

### Timestamps

Mutable entities use:

```text
created_at timestamptz NOT NULL
updated_at timestamptz NOT NULL
```

Append-only records may omit `updated_at` where mutation is explicitly forbidden.

### Optimistic Concurrency

Aggregates with meaningful concurrent writes should carry:

```text
version bigint NOT NULL DEFAULT 0
```

Updates must verify the expected version before replacing state.

## 4. Monetary Representation

Money is never stored as floating point.

Use integer minor units plus an explicit ISO currency code:

```text
amount_minor bigint NOT NULL
currency char(3) NOT NULL
```

Historical transactional records must store their own monetary snapshots.

## 9. Inventory Schema

### `inventory.inventory_item`

```text

product_variant_id UUID NULL
```

## 16. Risk, Store Operations and Intelligence

### `risk.risk_assessment`

Stores risk evaluation state and references the affected subject by stable ID/type rather than copying the authoritative subject.

### `store_operations.store_operation`

Stores operational workflow state associated with stores and operational activities.

### `intelligence.metric_definition`

Stores metric semantics and ownership. Materialised metrics/read models must not replace transactional sources of truth.

These tables will receive detailed field-level specifications when their corresponding services are designed.

## 17. Foreign-Key Policy

Foreign keys inside one aggregate and one persistence ownership boundary should normally be enforced by the database.

Cross-domain references are logical references and should not automatically create database-enforced foreign keys across service boundaries.

Example:

```text
commerce.order_item.product_id -> catalog.product.id
```

is a logical relationship. The Commerce service may validate the Product reference through an API/read model, while the physical databases remain independently deployable.

This prevents the database from becoming a hidden distributed transaction coordinator.

## 18. Indexing Requirements

Every aggregate root requires an index strategy based on its dominant access patterns.

Minimum expected indexes include:

```text
identity.session(customer_id, status)
household.membership(household_id, status)
household.membership(customer_id, status)
catalog.product(status)
catalog.product_variant(product_id, status)
inventory.inventory_item(store_id, product_id)
inventory.inventory_item(store_id, product_variant_id)
inventory.inventory_reservation(inventory_item_id, status)
inventory.inventory_reservation(expires_at, status)
commerce.cart(customer_id, status)
commerce.cart(household_id, status)
commerce.cart_item(cart_id)
commerce.checkout_session(cart_id, status)
commerce.checkout_session(expires_at, status)
commerce.order(customer_id, created_at)
commerce.order(household_id, created_at)
commerce.order_item(order_id)
payments.payment_transaction(order_id, created_at)
payments.payment_attempt(payment_transaction_id, attempt_number)
refunds.refund(order_id, created_at)
refunds.refund(payment_transaction_id, created_at)
fulfilment.fulfilment(order_id, status)
fulfilment.fulfilment_item(fulfilment_id)
delivery.delivery(order_id, status)
delivery.delivery_stop(delivery_id, sequence_number)
notifications.notification(customer_id, created_at)
notifications.notification_delivery(notification_id, channel)
ai_society.agent_capability(agent_id, capability)
ai_society.decision_record(subject_type, subject_id, created_at)
```

Indexes must be justified by real query patterns; indiscriminate indexing is prohibited because write-heavy aggregates such as Cart and Inventory are sensitive to index overhead.

## 19. Constraints and Invariants

Database constraints should enforce facts that are universally true and cheap to enforce.

Examples:

```text
quantity > 0
amount_minor >= 0
version >= 0
expires_at > created_at
sequence_number > 0
```

Business workflows that require coordination across domains must remain in services/process managers rather than being forced into giant database constraints.

## 20. State and Enum Strategy

Lifecycle states must use the authoritative vocabulary defined by Phase 2 and the domain/event architecture.

The first implementation should prefer validated text values or database enums only where the state vocabulary is stable and tightly owned.

A physical schema must never invent alternative spellings such as `completed` when the authoritative lifecycle uses `FULFILLED` without an explicit architecture decision.

## 21. Row Level Security

Where Supabase/PostgreSQL RLS is used:

- customers may access only records explicitly belonging to their customer identity or authorised household membership;
- one customer must not enumerate another customer's Orders, Carts, Payments, Refunds or Notifications;
- service roles may access only the schemas and tables required by their domain authority;
- AI execution identities must use explicit capability-based access rather than broad database ownership;
- administrative access must be auditable;
- public/anonymous database access must never expose authoritative transactional data.

RLS is a defence-in-depth boundary. It does not replace service-layer authorisation or domain ownership.

## 22. Audit and Temporal Data

Financial, security and AI decision records require append-oriented auditability.

Audit records must retain:

- actor or service identity;
- action/event type;
- subject identity;
- correlation ID;
- causation ID where available;
- timestamp;
- relevant before/after or immutable event references;
- outcome.

Do not use `updated_at` as a substitute for an audit trail.

## 23. Read Models

Read models may combine data from multiple domain owners for:

- customer order history;
- household dashboards;
- product discovery;
- Walk Mode navigation;
- AI context;
- operational dashboards;
- enterprise analytics.

Read models are disposable projections. They must be rebuildable from authoritative data/events and must never receive direct business writes that bypass the owning domain.

## 24. Migration Rules

All physical schema changes must be delivered as versioned migrations.

A migration must:

1. identify the owning domain;
2. identify the affected aggregate/entity;
3. preserve existing invariants;
4. preserve API/event compatibility where required;
5. define rollback or forward-recovery strategy;
6. avoid cross-domain transactional coupling;
7. include indexes and constraints deliberately;
8. include RLS changes where applicable;
9. include test coverage for material invariants.

Destructive migrations require an explicit compatibility/deprecation plan.

## 25. Phase 3.2 Acceptance Criteria

Phase 3.2 is complete when:

- every Phase 2 authoritative root has a physical persistence owner;
- aggregate child ownership is represented correctly;
- cross-domain references are explicitly distinguished from physical foreign keys;
- IDs and monetary values follow the enterprise strategy;
- core invariants have database-level enforcement where appropriate;
- required indexes are identified;
- RLS boundaries are defined;
- historical snapshots are immutable;
- Payment and Refund remain independent from Order;
- Inventory Reservation remains independent from Checkout and Inventory Item state;
- AI-derived data cannot become an alternate source of truth;
- the specification can be translated into migrations without reopening Phase 2 decisions.
