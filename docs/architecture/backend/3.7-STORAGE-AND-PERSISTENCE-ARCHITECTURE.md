# Phase 3.7 — Storage & Persistence Architecture

**Status:** Proposed
**Phase:** 3 — Backend Architecture
**Scope:** Enterprise-wide storage, persistence, consistency, and data-access architecture

## 1. Purpose

This document defines how Essentials Mart persists, owns, accesses, protects, and evolves operational data.

Storage decisions must follow the enterprise architecture, domain boundaries, aggregate boundaries, event contracts, and security model already established. Persistence must not become the mechanism by which bounded contexts are coupled together.

## 2. Core Principles

1. **Domain ownership is authoritative.** Each operational data set has one owning domain.
2. **Aggregate boundaries define transactional consistency.** A database transaction must not be used to erase domain boundaries.
3. **Services own their write models.** Other domains access data through contracts, commands, events, or explicitly approved read models.
4. **No shared mutable tables across domains.** Cross-domain convenience joins must not create hidden ownership.
5. **Operational and analytical workloads are separated.** AI, reporting, forecasting, and analytics must not overload transactional stores.
6. **Events are durable integration records.** Important state transitions must be recoverable and auditable.
7. **Persistence is replaceable.** Domain logic must not depend directly on a specific database vendor or driver.
8. **Security follows data sensitivity.** Access, encryption, retention, and audit requirements are determined by the data classification.
9. **History is preserved where required.** Financial, security, AI-decision, and other auditable records must not depend solely on mutable current-state rows.
10. **Schema evolution is deliberate.** Database migrations and event/schema changes are versioned and backward-compatible where required.

## 3. Storage Layers

Essentials Mart uses distinct storage roles rather than forcing every workload into one database.

### 3.1 Transactional Store

The primary source for domain-owned operational state.

Used for:

- Customers and household state
- Carts
- Checkout sessions
- Orders
- Payments and refunds
- Product/catalog state where owned by the relevant domain
- Inventory state
- Fulfilment and delivery state
- Other aggregate state requiring transactional guarantees

The transactional store is optimized for correctness, concurrency control, and predictable domain operations.

### 3.2 Event Store / Durable Event Log

Domain and integration events that are required for reliable asynchronous processing are persisted independently of transient application memory.

The event infrastructure supports:

- Ordered processing where required
- Replay where contractually safe
- Consumer offsets/checkpoints
- Idempotent consumers
- Dead-letter handling
- Correlation and causation identifiers
- Event versioning
- Audit reconstruction

An event is not considered reliably published merely because application code successfully executed an in-memory callback.

### 3.3 Read Models

Read models are derived projections optimized for specific query workloads.

Examples include:

- Customer order history
- Product availability views
- Store inventory views
- Delivery tracking views
- Walk Mode navigation data
- AI recommendation inputs
- Operational dashboards

A read model does not become the authoritative owner merely because it is queried frequently.

### 3.4 Analytical Storage

Analytics, forecasting, experimentation, enterprise intelligence, and long-running AI workloads use analytical storage derived from operational data.

Analytical workloads must not perform uncontrolled queries against transactional write stores.

### 3.5 Object Storage

Object storage is used for large binary or document-oriented data such as:

- Product media
- Store layout assets
- Walk Mode spatial assets
- Documents
- Export files
- AI evaluation artifacts
- Other large immutable or versioned assets

Object storage references belong in domain-owned metadata records; large binary payloads should not be embedded in transactional rows unless explicitly justified.

## 4. Domain Ownership

Each bounded context defines its own persistence boundary.

Examples:

| Domain | Authoritative data examples |
|---|---|
| Commerce | Cart, Checkout Session, Order |
| Payment | Payment Transaction, payment state |
| Refund | Refund state and refund workflow |
| Product | Product catalogue state |
| Inventory | Stock levels, reservations, holds |
| Fulfilment | Fulfilment state and operational tasks |
| Delivery | Delivery assignments, routes, delivery state |
| Customer/Household | Customer and household state |
| Identity | Identity and authentication records |
| AI Society | Agent configuration, capability and governance metadata |
| Intelligence | Intelligence outputs, model metadata, evaluation records where owned |

These boundaries are architectural ownership rules, not merely proposed table prefixes.

## 5. Aggregate Persistence

Each aggregate root is persisted as the consistency boundary appropriate to its domain.

For example:

- Cart owns Cart Items.
- Checkout Session owns its checkout state and frozen checkout information.
- Order owns Order Items and historical purchase snapshots.
- Payment Transaction owns its payment state and gateway references.
- Refund owns its refund workflow and references the related payment/order by ID.

Child entities and value objects must not be independently modified through repositories when the aggregate root owns their lifecycle.

## 6. IDs and References

Cross-domain relationships use stable identifiers rather than foreign-key coupling between independent domain stores.

A domain may retain:

- Its own aggregate ID
- External aggregate IDs required for integration
- Correlation IDs
- Causation IDs
- Idempotency keys
- External provider references

A reference to another domain's ID does not transfer ownership of the referenced entity.

## 7. Transactions and Consistency

### Strong consistency

Use a single transactional boundary when an invariant must hold immediately within one aggregate or explicitly defined local transaction.

Examples:

- Cart item mutation
- Checkout state transition within the checkout boundary
- Order creation and its owned order items
- Payment state transition within the payment boundary

### Eventual consistency

Use events when state crosses domain boundaries.

Examples:

- Checkout requests inventory reservation
- Payment success causes order state progression
- Order placement initiates fulfilment
- Fulfilment changes drive delivery coordination
- Operational events feed analytical and AI projections

Distributed transactions are not the default architecture.

## 8. Outbox and Reliable Publication

Where a domain changes transactional state and must publish an event reliably, the implementation should use a transactional outbox or equivalent atomic persistence mechanism.

The required sequence is conceptually:

1. Persist domain state change.
2. Persist the event/outbox record in the same local transaction.
3. Commit once.
4. Publish the event asynchronously.
5. Mark the outbox record as published.
6. Retry safely when publication fails.

Consumers must be idempotent because delivery may occur more than once.

## 9. Concurrency and Idempotency

Persistence implementations must explicitly handle concurrent writes.

Strategies may include:

- Optimistic concurrency/version columns
- Conditional updates
- Unique constraints
- Database transactions
- Explicit locks where genuinely necessary
- Idempotency keys for externally retried commands

The development in-memory adapters must not be treated as evidence of production atomicity. Production persistence must implement the consistency guarantees required by the relevant aggregate.

## 10. Data Integrity

Database constraints should enforce invariants that are appropriately persistence-level concerns.

Examples:

- Unique identifiers
- Required fields
- Valid state combinations where practical
- Referential integrity inside one ownership boundary
- Monetary precision and currency representation
- Idempotency uniqueness
- Version/concurrency checks

Business invariants remain enforced in the domain/application layer and must not rely exclusively on database constraints.

## 11. Monetary Data

Money must be persisted as exact integer minor units plus an explicit currency code or an equivalent lossless representation.

Floating-point storage is prohibited for financial amounts.

Historical monetary snapshots required by Orders, Payments, and Refunds must remain immutable once committed, subject to explicit correction/audit mechanisms.

## 12. Security and Privacy

Sensitive persistence must support:

- Encryption in transit
- Encryption at rest
- Least-privilege database credentials
- Domain/service-specific access
- Secret isolation
- Audit logging for sensitive operations
- Retention and deletion policies
- Controlled administrative access

Application APIs must not expose database credentials, internal storage topology, or unrestricted query capabilities to clients or AI agents.

## 13. AI Data Access

AI agents and Intelligence Engines do not receive unrestricted access to operational databases.

AI access should occur through:

- Domain APIs
- Approved read models
- Explicit tools/capabilities
- Governed analytical datasets
- Sanitized event streams

Write operations require explicit authority and must pass through domain-owned application boundaries.

This prevents AI reasoning from becoming an uncontrolled database mutation mechanism.

## 14. Caching

Caching is an optimization, never an alternative source of truth.

Cache design must define:

- Owner of the underlying data
- Cache key
- TTL
- Invalidation/update strategy
- Acceptable staleness
- Failure behavior
- Security classification

Sensitive customer, payment, identity, and authorization data must not be cached without an explicit security and lifecycle decision.

## 15. Backups and Disaster Recovery

Production persistence must define:

- Automated backups
- Point-in-time recovery where required
- Replication strategy
- Recovery Point Objective (RPO)
- Recovery Time Objective (RTO)
- Restore testing
- Regional failure strategy where required
- Disaster-recovery ownership

A backup that has never been successfully restored is not considered a proven recovery mechanism.

## 16. Retention and Lifecycle

Every major data class must eventually have an explicit lifecycle policy covering:

- Creation
- Active use
- Archival
- Retention period
- Deletion or anonymisation
- Legal/audit holds where applicable

Financial and audit records require stronger retention guarantees than ephemeral application state such as abandoned carts.

## 17. Migration and Schema Evolution

All production schema changes must be version controlled and deployed through migrations.

Migrations must account for:

- Existing data
- Backward compatibility
- Rolling deployments
- Event consumers using older schemas
- Rollback or forward-fix strategy
- Large-table migration safety

Destructive changes require explicit architectural review.

## 18. Repository and Data-Access Pattern

Domain/application code depends on repository or port interfaces rather than database-specific implementations.

Conceptually:

```text
Domain/Application
       │
       ▼
Repository / Persistence Port
       │
       ▼
Infrastructure Adapter
       │
       ├── PostgreSQL / transactional DB
       ├── Event infrastructure
       ├── Object storage
       ├── Cache
       └── Analytical storage
```

The infrastructure layer may change without rewriting domain rules.

## 19. Observability and Audit

Persistence operations must integrate with the platform observability architecture.

Relevant records should carry:

- Request ID
- Correlation ID
- Causation ID
- Actor/service identity
- Aggregate ID
- Event ID where applicable
- Timestamp
- Schema/version information

Security-sensitive and financially significant mutations must produce an auditable trail.

## 20. Failure Handling

Storage failures must fail safely.

The platform must distinguish between:

- Temporary connectivity failures
- Serialization/concurrency conflicts
- Constraint violations
- Timeouts
- Capacity failures
- Permanent validation failures
- Corruption or integrity failures

Retry policies must be bounded and idempotency-aware. A retry must never blindly duplicate a financial or operational command.

## 21. Development vs Production

In-memory adapters remain useful for local development and deterministic tests, but they are explicitly non-production implementations.

Production readiness requires real persistence implementations that satisfy the aggregate, concurrency, durability, security, backup, and recovery guarantees defined by this architecture.

## 22. Architectural Consequences

This architecture intentionally accepts additional infrastructure complexity in exchange for:

- Clear domain ownership
- Safer evolution
- Reliable event publication
- Scalable read workloads
- Stronger financial correctness
- Better AI governance
- Better auditability
- Easier infrastructure replacement
- Reduced cross-domain coupling

The database is therefore an implementation of the enterprise model, not the model itself.

## 23. Dependencies

This architecture depends on and must remain consistent with:

- Enterprise Architecture principles
- Domain-Driven Enterprise Architecture
- Event-Driven Architecture
- API & Service Architecture
- Data Ownership & Database Boundaries
- Security & Anti-Replication Architecture
- Observability, Auditability & Trust Architecture
- Scalability & Multi-Store Architecture
- AI Society Architecture
- Intelligence Engine Architecture
- AI Agent Governance & Permissions
- Human-in-the-Loop Architecture

Any future persistence decision that changes domain ownership, aggregate boundaries, event semantics, security controls, or audit guarantees must trigger a forward-consistency review of the affected architecture documents.

## 24. Decision

Essentials Mart will use domain-owned persistence boundaries with transactional storage for operational state, durable event infrastructure for asynchronous integration, purpose-built read models for high-volume queries, analytical storage for intelligence workloads, and object storage for large assets.

No storage technology may override or silently weaken the enterprise domain, aggregate, security, audit, or event boundaries established by the architecture.
