# Phase 3.4 — API Architecture & Contracts

## Status

Proposed — derived from the enterprise architecture, ADRs, Phase 2 information architecture, database architecture, and service architecture.

## 1. Purpose

This document defines the API boundary for Essentials Mart. APIs expose capabilities owned by backend services without exposing database structure or aggregate internals.

The API layer is a contract boundary, not a pass-through to persistence.

## 2. API Principles

1. APIs are organized around domain capabilities, not database tables.
2. Every mutable resource has one authoritative service owner.
3. Request and response DTOs are explicit and versionable.
4. Domain objects are never serialized directly as public contracts.
5. Authentication and authorization are enforced before sensitive domain operations.
6. Commands that may be retried must support idempotency where appropriate.
7. Errors use stable machine-readable codes; human messages remain descriptive and changeable.
8. API consumers must not infer business state from HTTP status alone; response codes and resource state are both authoritative.
9. Cross-service workflows are represented through commands/events rather than clients orchestrating internal database operations.
10. Internal service APIs and external/public APIs may differ; internal implementation details must not leak into public contracts.

## 3. API Layers

```text
Flutter / Web / WhatsApp / Trusted Integrations
                    |
                    v
              API Gateway
                    |
        Authentication / Authorization
                    |
                    v
             Domain API Layer
                    |
          Application Services
                    |
               Aggregates
                    |
             Owned Storage
```

The gateway may provide routing, rate limiting, request correlation, and coarse policy enforcement. Domain services remain responsible for domain authorization and invariants.

## 5. Commerce API Surface

The initial commerce API is intentionally small and maps to the existing service implementation.

### Products

`GET /products/:productId`

Returns the public Product DTO.

`GET /products`

Returns a product collection/read model. Filtering, pagination and search capabilities must be explicitly defined before production use.

### Basket

`GET /basket`

Returns the authenticated customer's current basket.

`POST /basket/items`

Adds a product to the authenticated customer's basket.

Request:

```json
{
  "productId": "bread",
  "quantity": 2
}
```

`DELETE /basket/items/:productId`

Removes the product line from the authenticated customer's basket.

### Checkout / Orders

`POST /checkout`

Creates an order through the checkout workflow according to the current checkout implementation. Production evolution must move toward an explicit Checkout Session resource before introducing payment orchestration.

`GET /orders/:orderId`

Returns an order only when the authenticated principal is authorized to access it. Ownership must be enforced in the owning repository/service boundary, not by fetching another customer's order and filtering it afterward.

## 7. Command vs Query Rules

### Queries

Queries retrieve authorized representations or read models and must not mutate business state.

### Commands

Commands request a business action. They are validated by the owning service and may produce domain events.

Examples:

- AddCartItem
- InitiateCheckout
- ReserveInventory
- InitiatePayment
- ApproveRefund
- AssignDelivery

The API may expose a REST-shaped endpoint, but internally the request is handled as a domain/application command.

## 8. Idempotency

Commands involving financial, inventory, fulfillment, delivery, or external provider effects must be designed for retry safety.

The API will support an idempotency key for operations where duplicate execution could create an incorrect business outcome.

Example:

```text
Idempotency-Key: 7f0c...unique-operation-key...
```

The owning service persists the result associated with the key within its own consistency boundary. An idempotency key must never be used as a substitute for authorization.

## 9. Authentication and Authorization

Every protected API request carries an authenticated principal established by the Identity/Auth boundary.

Authorization is evaluated using the resource owner, household role, service policy, and relevant business rules.

Examples:

- A customer may access only their authorized orders.
- Household resources require appropriate household membership/role.
- Store operations require store/operator permissions.
- Enterprise intelligence access requires enterprise authorization.
- AI agents inherit explicit capabilities and may not gain authority merely because they can call an API.

## 10. Error Contract

All API errors use a stable structure:

```json
{
  "error": {
    "code": "NOT_FOUND",
    "message": "Order not found"
  }
}
```

`code` is machine-readable and stable. `message` is human-readable and may be changed without changing API behavior.

Domain errors must carry explicit error codes. HTTP status mapping must never depend on matching free-form exception messages.

Typical categories include:

- `VALIDATION_ERROR`
- `UNAUTHENTICATED`
- `FORBIDDEN`
- `NOT_FOUND`
- `CONFLICT`
- `BASKET_EMPTY`
- `INVALID_QUANTITY`
- `PRODUCT_UNAVAILABLE`
- `STALE_PRICE`
- `INTERNAL`

## 11. Versioning

The public API will use explicit versioning once external consumers depend on it.

Initial production direction:

```text
/api/v1/...
```

Breaking changes require a new major API version or an explicitly managed compatibility strategy. Additive changes should remain backward compatible where practical.

Internal service contracts may evolve independently provided their consumers are controlled and compatibility is maintained during deployment transitions.

## 12. Pagination and Collection Contracts

Collection endpoints must use explicit pagination rather than returning unbounded datasets.

The production contract should support a stable cursor-based model for high-growth resources:

```json
{
  "items": [],
  "nextCursor": "...",
  "hasMore": true
}
```

Offset pagination may be used for bounded administrative/read-model queries where appropriate.

## 13. Events Are Not Public API Responses

Domain events and API responses serve different purposes.

An API response describes the result of a client request. An event announces a fact that occurred in the system.

For example:

```text
POST /checkout
        |
        v
Checkout application command
        |
        v
CheckoutCompleted / OrderCreated
        |
        +--> Inventory
        +--> Payment
        +--> Notification
        +--> Audit
```

Authoritative event names must come from the established enterprise event vocabulary. Services must not invent conflicting event names merely to match endpoint names.

## 14. Webhooks

External webhook endpoints are owned by the service responsible for the external relationship.

Examples:

- PSP webhook → Payment Service
- Delivery provider webhook → Delivery Service
- WhatsApp provider webhook → WhatsApp Integration Service

Webhook handlers must:

- authenticate/verify the provider request;
- validate payloads;
- be idempotent;
- persist enough information to safely process retries;
- publish internal domain events after successful processing;
- never expose provider-specific payload structures as enterprise contracts.

## 15. AI Access to APIs

The AI Society uses the same authoritative service boundaries as human clients.

AI agents may:

- query authorized read models;
- request permitted commands;
- receive domain events;
- ask for human approval when required.

AI agents may not:

- bypass authorization;
- write directly to databases;
- call privileged internal endpoints without an explicit capability;
- change financial, inventory, or household state outside their delegated authority.

Every consequential AI action must remain attributable to the agent, capability, principal, and originating request/context.

## 16. WhatsApp as an API Channel

WhatsApp is a transport/channel into the platform, not a parallel application architecture.

A WhatsApp request is normalized into the same command/query model used by other clients. The originating channel and consent context are preserved for auditability.

This allows a user with limited app connectivity to access authorized Essentials Mart capabilities without creating a second business-logic implementation.

## 17. API Security Requirements

Production APIs must include, as applicable:

- TLS
- authentication
- authorization
- request validation
- content-type enforcement
- payload-size limits
- rate limiting
- idempotency for retry-sensitive commands
- correlation/request IDs
- structured audit logging
- safe error responses
- secret isolation
- provider webhook verification

Sensitive business logic remains server-side.

## 18. API Contract Testing

API tests must verify:

1. authentication behavior;
2. authorization and ownership isolation;
3. request validation;
4. response DTO shape;
5. stable error codes;
6. status-code semantics;
7. idempotency where required;
8. malformed/oversized payload handling;
9. webhook verification and replay handling;
10. compatibility of versioned contracts.

Tests must assert meaningful business invariants rather than merely accepting broad ranges of possible outcomes.

## 19. API Documentation

The authoritative API specification will ultimately be represented in an OpenAPI-compatible contract generated or maintained from the service boundary.

The OpenAPI document must describe:

- endpoints;
- methods;
- authentication requirements;
- request schemas;
- response schemas;
- error schemas;
- status codes;
- idempotency requirements;
- pagination;
- webhook contracts;
- versioning.

The specification must not become a substitute for domain architecture; it describes the interface to architecture already established elsewhere.

## 20. Phase 3.4 Exit Criteria

Phase 3.4 is complete when:

- each public API capability has an authoritative service owner;
- request/response DTO boundaries are explicit;
- command/query semantics are defined;
- authentication and authorization boundaries are defined;
- stable error-code rules are established;
- idempotency requirements are defined;
- webhook ownership is defined;
- AI and WhatsApp access follow the same service boundaries;
- API versioning strategy is established;
- the API can be translated into OpenAPI contracts without inventing new domain ownership.
