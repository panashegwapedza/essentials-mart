# Phase 3.9 — API Gateway, Edge & Service Communication Architecture

**Status:** Accepted  
**Phase:** 3 — Backend Architecture  
**Depends on:** Enterprise Architecture, EIP, ADRs, Phase 2 Information Architecture, Phase 3.1–3.8

## 1. Purpose

Define how clients, external systems, and backend services communicate while preserving domain ownership, security boundaries, observability, and independent service evolution.

## 2. Communication Model

Essentials Mart uses two primary communication modes:

- **Synchronous communication** for request/response operations requiring an immediate result.
- **Asynchronous communication** for workflows that cross bounded contexts, tolerate eventual consistency, or require durable event processing.

The choice is architectural, not merely an implementation detail.

```text
Client / External System
          |
          v
     [Edge Layer]
          |
          v
   [API Gateway / BFF]
          |
    +-----+-----+
    |     |     |
    v     v     v
 Domain  Domain Domain
 Service Service Service
    |     |     |
    +-----+-----+
          |
          v
   Event / Command Bus
```

## 3. Edge Layer

The edge layer is the externally exposed boundary of the platform.

It is responsible for concerns such as:

- TLS termination where applicable;
- request routing;
- rate limiting;
- request-size limits;
- basic protocol validation;
- abuse protection;
- correlation identifiers;
- authentication handoff;
- observability context;
- controlled exposure of public endpoints.

Business rules must not be implemented in the edge layer.

## 4. API Gateway

The API Gateway provides a controlled entry point into backend capabilities.

It may perform:

- routing;
- authentication enforcement;
- authorisation preconditions;
- rate limiting;
- API version routing;
- request correlation;
- response normalization where appropriate;
- tenant/store context propagation;
- observability instrumentation.

It must not become a second domain layer containing duplicated business logic.

## 5. Backend-for-Frontend Boundaries

Where client-specific composition is required, a BFF may be introduced.

A BFF exists to adapt backend capabilities to a client experience. It does not own domain state and must not become the authoritative source of business rules.

Examples may include:

- Flutter mobile BFF/API surface;
- WhatsApp interaction gateway;
- enterprise/operations API surface.

Shared business behaviour remains in domain/application services.

## 6. API Contract Principles

External APIs must:

- expose explicit DTOs rather than internal domain objects;
- use stable identifiers;
- use documented error codes;
- validate inputs at the boundary;
- enforce authentication and authorization;
- support idempotency where operations can be retried;
- define pagination for collection endpoints;
- define timeout behaviour;
- define version/evolution strategy;
- avoid leaking persistence implementation details.

API contracts are architecture-controlled interfaces, not accidental representations of database schemas.

## 7. Authentication and Authorization

Authentication establishes who is making a request. Authorization establishes what that principal is allowed to do.

The edge may authenticate or validate credentials, but authoritative authorization remains enforced by the service owning the protected resource.

A downstream service must not assume that because a request passed through the gateway it is automatically authorized for every operation.

## 8. Service-to-Service Communication

Services communicate through explicit contracts.

Preferred mechanisms are:

1. synchronous API calls when an immediate response is required;
2. asynchronous commands/events when decoupling and eventual consistency are appropriate.

A service must not access another service's private database tables as a communication mechanism.

## 9. Synchronous Communication Rules

Synchronous calls must have:

- explicit timeouts;
- bounded retries where safe;
- idempotency where retries may repeat mutations;
- correlation IDs;
- failure classification;
- dependency health visibility.

Retries must not amplify load or duplicate financial/transactional operations.

Circuit breaking, bulkheads, and backpressure should be introduced where dependency failure could cascade through the platform.

## 10. Asynchronous Communication Rules

Events and commands should be used when a workflow crosses domain boundaries without requiring an immediate synchronous response.

Consumers must tolerate:

- duplicate delivery;
- retries;
- out-of-order delivery where the contract permits it;
- delayed delivery;
- poison messages;
- consumer downtime.

Handlers must be idempotent where duplicate processing is possible.

## 11. Commands vs Events

A **command** requests that an owning service perform an action.

An **event** records that something has happened.

Commands must have an identified target/owner. Events must use the authoritative event vocabulary defined by the enterprise architecture and EIP corpus.

Services must not invent competing event names for the same domain fact.

## 12. Cross-Domain Boundary Example

A commerce checkout should not directly modify inventory or payment persistence.

Instead:

```text
Checkout Service
      |
      +---- command/event ----> Inventory
      |
      +---- command/event ----> Payment
      |
      +---- event -----------> Order / downstream consumers
```

Each receiving domain owns its own state transition and emits its own authoritative facts.

## 13. Event Delivery

Where an operation changes durable state and publishes an event, the architecture should use an outbox or equivalent durable publication mechanism so that database state and event publication cannot silently diverge.

Consumers should maintain sufficient processing state to support idempotency and recovery.

## 14. API Versioning

API evolution must preserve existing clients whenever practical.

Breaking changes require an explicit versioning/migration strategy.

Versioning should be applied at the contract boundary rather than creating arbitrary copies of domain logic.

Deprecated API versions must have a documented retirement policy.

## 15. Rate Limiting and Abuse Protection

Rate limits should be applied according to risk and workload characteristics.

Higher-risk operations may require stricter controls than read-only operations.

Examples include:

- authentication attempts;
- checkout/payment operations;
- account recovery;
- AI requests;
- messaging/WhatsApp interactions;
- high-volume catalog queries.

Rate limiting is a protection mechanism and must not replace authorization.

## 16. Timeouts and Failure Propagation

Every network dependency must have an explicit timeout policy.

A downstream timeout must not cause an unbounded request to remain open or consume resources indefinitely.

Failure responses must distinguish between:

- invalid client input;
- unauthorized/forbidden requests;
- unavailable dependencies;
- transient failures;
- permanent business failures;
- internal failures.

Internal implementation details and sensitive information must not be returned to clients.

## 17. Correlation and Trace Context

Requests entering the platform receive or propagate a correlation identifier.

The identifier and trace context should follow synchronous and asynchronous boundaries so that one customer action can be reconstructed across:

```text
Client → Gateway → Service → Event → Consumer → External Provider
```

This integrates with the observability and auditability architecture.

## 18. Security Boundaries

The edge is a security boundary, but not the only one.

Services must apply defense in depth:

- authenticate trusted service identities where required;
- authorize operations locally;
- validate payloads;
- enforce resource ownership;
- prevent SSRF and unsafe outbound access where applicable;
- protect internal endpoints from public exposure;
- avoid trusting client-provided identity or ownership fields.

## 19. External Channels

External channels such as Flutter, web clients, WhatsApp, enterprise integrations, and future partner APIs must enter through controlled interfaces.

WhatsApp and similar channels are interaction surfaces, not privileged backend identities. The channel adapter translates user intent into authorized platform operations through the same domain boundaries as other clients.

## 20. AI Communication

AI agents do not receive unrestricted service or database access.

AI actions are mediated through approved capabilities/tools and authorization policies defined by the AI Society architecture.

An AI agent requesting a commerce operation therefore follows the same service and authorization boundaries as an ordinary client request, with additional AI capability and audit context.

## 21. Performance and Scalability

The communication architecture must support horizontal scaling without requiring shared mutable in-process state between service instances.

Traffic management should account for:

- bursty shopping traffic;
- promotional events;
- Walk Mode interactions;
- AI workloads;
- asynchronous event processing;
- external provider latency.

Expensive operations should be moved to asynchronous workflows where an immediate response is not architecturally required.

## 22. Observability

Communication infrastructure must expose:

- request rates;
- latency;
- error rates;
- dependency failures;
- retry counts;
- queue/event lag;
- rate-limit activity;
- correlation/trace identifiers;
- deployment/version metadata.

Sensitive payloads must not be logged merely for debugging convenience.

## 23. Rules

1. The edge is a boundary, not a business-logic layer.
2. API Gateway routing must not duplicate domain ownership.
3. BFFs adapt experiences; they do not own domain state.
4. Resource-owning services enforce authorization.
5. Services never communicate by directly accessing another service's private database.
6. Synchronous calls require bounded timeouts and safe retry semantics.
7. Asynchronous consumers must be designed for retries and duplicate delivery.
8. Commands request actions; events describe facts.
9. Durable state changes that publish events should use an outbox or equivalent mechanism.
10. APIs expose explicit contracts and DTOs.
11. AI capabilities operate through governed service boundaries.
12. External channels do not receive privileged access merely because they are trusted interfaces.
13. Correlation and trace context cross service and event boundaries.
14. Failure propagation must be bounded and observable.
15. Communication architecture must preserve domain and aggregate ownership established in Phase 2.

## 24. Phase 3.9 Exit Criteria

Phase 3.9 is complete when:

- edge responsibilities are explicit;
- gateway/BFF responsibilities are bounded;
- API contract rules are explicit;
- synchronous and asynchronous communication rules are defined;
- command/event semantics are defined;
- service-to-service database bypass is prohibited;
- timeout/retry/idempotency principles are defined;
- API evolution is governed;
- external channel integration is bounded;
- AI communication follows governed capabilities;
- observability and failure propagation requirements are defined.
