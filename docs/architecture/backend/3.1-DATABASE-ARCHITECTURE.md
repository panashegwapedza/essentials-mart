# Essentials Mart — Database Architecture

**Status:** Defined — Phase 3.1
**Phase:** 3 — Backend Architecture

## Purpose

This document defines the logical database architecture derived from the frozen Phase 2 information model. It establishes persistence ownership, transactional boundaries, integrity rules, and the constraints that a physical database implementation must preserve.

The database implements the architecture; it does not redefine domain ownership.

## Governing Principles

1. Each authoritative aggregate has one persistence owner.
2. Aggregate boundaries define transactional boundaries unless an explicit architectural decision states otherwise.
3. Independent domains must not share mutable tables as a substitute for integration.
4. Cross-domain relationships use stable opaque IDs and events/API contracts.
5. Historical transactional snapshots are immutable.
6. Read models may denormalise data for performance but are never authoritative.
7. Database constraints enforce invariants that belong inside the persistence boundary.
8. External identifiers remain separate from internal entity IDs.
9. Financial and audit records require durable history and must not depend on mutable operational state.
10. AI-derived data is explicitly derived, attributable and independently lifecycle-managed.

## Aggregate Persistence Rules

### Cart

Cart and Cart Item persist within the Commerce boundary. Cart mutation is independently transactional from Checkout and Order.

A checkout failure must not implicitly delete or mutate the cart beyond explicitly defined checkout behaviour.

### Checkout Session

Checkout Session is independently persisted as short-lived process state. It contains frozen checkout context rather than pointers to mutable cart values as the authoritative purchase record.

It may record product/price/tax/shipping snapshots necessary to reproduce the checkout decision.

### Order

Order and Order Item are persisted as the durable commercial transaction. Order Items contain historical snapshots required to explain the transaction without rereading mutable Product state.

Order persistence must not depend on a live Product row remaining unchanged.

### Payment

Payment Transaction and Payment Attempt are persisted independently from Order. PSP identifiers, gateway responses, idempotency information and settlement state belong to the Payments boundary.

Payment persistence must support retries and asynchronous webhook processing without requiring mutation of Order internals.

### Refund

Refund is independently persisted. Multiple refunds may reference the same Order and Payment Transaction. Refund state must support partial amounts, approval/workflow state and asynchronous settlement.

## Cross-Domain References

Logical references include:

```text
Order.customerId -> CustomerId
OrderItem.productId -> ProductId
InventoryItem.productId -> ProductId
InventoryItem.storeId -> StoreId
PaymentTransaction.orderId -> OrderId
Refund.paymentTransactionId -> PaymentTransactionId
Refund.orderId -> OrderId
Fulfilment.orderId -> OrderId
Delivery.orderId -> OrderId
Notification.customerId -> CustomerId
AI Decision Record.actorAgentId -> AgentId
```

These references do not automatically require cross-service foreign keys. A physical implementation must preserve ownership and service independence.

## Transaction Boundaries

Strong consistency is required within an aggregate for operations such as:

- Cart item mutation and cart totals;
- Checkout state transitions owned by Checkout;
- Order creation and immutable Order Item creation;
- Payment Transaction state transitions owned by Payments;
- Refund state transitions owned by Refunds;
- Inventory reservation state transitions owned by Inventory.

Cross-domain workflows use events, commands or explicit service APIs rather than distributed database transactions wherever practical.

## Inventory Reservation

Inventory reservation is a first-class persisted state with an expiry/TTL concept.

The intended flow is:

```text
Checkout
   ↓
Inventory Hold Requested
   ↓
Inventory Reservation
   ↓
Reservation Confirmed / Expired / Released
```

A reservation must be idempotently identifiable and must prevent duplicate consumption of the same stock according to the eventual physical inventory implementation.

## Identity and Keys

All authoritative entities use the Phase 2 ID strategy:

- immutable;
- opaque;
- stable;
- globally suitable for distributed operation;
- independent of mutable names or business labels.

Internal entity IDs must not be reused for PSP, supplier, marketplace or external-system identifiers.

Database-generated surrogate keys may exist as physical implementation details where justified, but they must not replace the authoritative domain identity exposed through domain contracts.

## Integrity Constraints

The physical schema must enforce, where applicable:

- unique authoritative entity IDs;
- aggregate-child ownership;
- non-negative monetary quantities where applicable;
- valid currency representation;
- positive quantities for order/cart lines;
- immutable historical snapshots;
- reservation expiry semantics;
- valid lifecycle state transitions;
- idempotency-key uniqueness within its defined scope;
- audit record append-only behaviour where required.

## Monetary Data

Money must be represented using integer minor units plus an explicit currency code rather than floating-point database values.

Historical transactional money must be stored with the transaction snapshot. Current Product pricing must never be used to reconstruct historical Order totals.

## Auditability

Financial, security, AI-decision and significant state-transition records require durable audit information sufficient to establish:

- what happened;
- when it happened;
- which entity was affected;
- which actor or service initiated it;
- correlation/causation context where applicable;
- relevant idempotency information.

Audit records must not become a mechanism for rewriting operational ownership.

## Read Models

Read models may combine data from multiple domains for:

- customer order history;
- household dashboards;
- Walk Mode navigation;
- inventory availability views;
- AI context;
- enterprise analytics.

They are projections and may be rebuilt from authoritative records/events. They must not be written as if they were authoritative operational entities.

## AI Data Boundary

AI Society may persist derived artefacts such as recommendations, embeddings, preferences, forecasts, working memory and decision records.

Each derived artefact must identify its provenance and lifecycle. AI persistence must not grant an AI agent direct ownership of Customer, Order, Payment, Inventory or other operational state.

## Security and Isolation

Physical database design must align with domain/service authorization boundaries. Sensitive identity credentials, payment data and audit records require stricter access controls than ordinary catalogue/read data.

Where row-level security is used, policies must express ownership and authorization rules rather than merely hiding UI routes.

## Physical Database Constraint

Phase 3 implementation must proceed in this order:

```text
Logical database architecture
        ↓
Persistence/schema specification
        ↓
Indexes + constraints + RLS/security policies
        ↓
Migration design
        ↓
Implementation
        ↓
Integration tests
```

No physical table should be introduced merely because an entity appears in the catalogue. The physical design must follow aggregate ownership and access patterns.

## Phase 3.1 Exit Criteria

Phase 3.1 is complete when the implementation team can answer, for every authoritative entity:

1. Which domain owns it?
2. Which aggregate owns it?
3. Which persistence boundary stores it?
4. Which transaction boundary governs its mutation?
5. Which IDs reference it?
6. Which events communicate its state changes?
7. Which historical data must remain immutable?
8. Which security boundary protects it?
9. Which read models may project it?

These answers must remain consistent with the frozen Phase 2 information architecture and the approved EDA/ADR/EIP corpus.
