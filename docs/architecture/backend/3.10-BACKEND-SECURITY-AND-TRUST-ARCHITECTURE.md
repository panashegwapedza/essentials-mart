# Phase 3.10 — Backend Security & Trust Architecture

**Status:** Accepted  
**Phase:** 3 — Backend Architecture  
**Depends on:** Enterprise Architecture, EIP, ADRs, Phase 2 Information Architecture, Phase 3.1–3.9

## 1. Purpose

Define the security and trust model for the Essentials Mart backend so that identity, authorization, data, services, AI capabilities, integrations, and operational infrastructure are protected by explicit and enforceable boundaries.

Security is treated as an architectural property rather than a feature added after implementation.

## 2. Security Principles

Essentials Mart follows these principles:

1. Deny by default.
2. Least privilege.
3. Verify at every trust boundary.
4. Never trust client-controlled ownership or authority claims.
5. Keep sensitive business logic server-side.
6. Minimize sensitive data collection and exposure.
7. Separate authentication from authorization.
8. Treat service identities as distinct from user identities.
9. Fail closed when security configuration is ambiguous or invalid.
10. Make security-relevant actions observable and auditable.
11. Assume external dependencies can fail or become compromised.
12. Design for credential rotation and key replacement.

## 3. Trust Zones

The backend is divided into explicit trust zones:

```text
[Untrusted / External]
        |
        v
[Edge / Gateway]
        |
        v
[Authenticated Application Boundary]
        |
   +----+----+
   |         |
   v         v
[Domain]   [AI Capability Boundary]
   |         |
   +----+----+
        |
        v
[Data / Event Infrastructure]
        |
        v
[External Providers]
```

Crossing a trust boundary requires explicit validation and authorization.

## 4. Identity

Every authenticated principal has an explicit identity and principal type.

Possible principal categories include:

- customer;
- household member;
- store/operator user;
- enterprise user;
- administrator;
- service identity;
- controlled AI agent identity.

Identity must not be inferred from mutable client payload fields.

## 5. Authentication

Authentication establishes the identity associated with a request.

Supported authentication mechanisms must be selected according to channel and risk, while preserving a common principal model across the platform.

Authentication configuration must fail closed in production. Development authentication is an explicit local-development capability and must never become an accidental production fallback.

## 6. Authorization

Authorization is evaluated against:

- principal identity;
- principal type;
- requested capability;
- resource ownership;
- domain policy;
- tenant/store scope where applicable;
- operational state;
- contextual risk controls.

Authorization belongs to the resource-owning service and cannot be delegated entirely to the API Gateway.

## 7. Resource Ownership

Services must enforce ownership at the data-access boundary wherever possible.

For example:

```text
getOwnedById(customerId, orderId)
```

is preferred to retrieving an arbitrary order and filtering ownership afterward.

This reduces enumeration risk and ensures the persistence implementation can enforce ownership directly.

## 8. Service Identity

Backend services communicate using explicit service identities rather than impersonating arbitrary end users.

Service credentials must be:

- scoped;
- short-lived where practical;
- rotatable;
- stored outside source control;
- auditable;
- rejected when expired or invalid.

A service identity does not automatically inherit every permission available to a human administrator.

## 9. Secrets and Key Management

Secrets must never be committed to source control.

Secret material includes:

- API keys;
- database credentials;
- signing keys;
- webhook secrets;
- service credentials;
- payment-provider credentials;
- encryption keys.

Secrets must be injected through controlled environment/configuration mechanisms or a dedicated secret-management system.

Rotation must be possible without requiring application source changes.

## 10. Data Protection

Sensitive data must be protected according to its classification.

Controls may include:

- encryption in transit;
- encryption at rest;
- field-level protection where warranted;
- access controls;
- retention limits;
- controlled exports;
- deletion/anonymization workflows.

The system should avoid storing information that is not necessary for a defined business purpose.

## 11. Payment Security

Payment credentials and sensitive payment-provider secrets must not be handled by ordinary commerce application code unless explicitly required and appropriately protected.

Payment integrations should prefer provider-hosted/tokenized mechanisms where appropriate.

Payment webhooks must be authenticated using provider-specific signature verification or equivalent controls before changing financial state.

Client claims of payment success are never authoritative.

## 12. Webhook Security

Inbound webhooks must:

- verify authenticity;
- validate payload structure;
- enforce replay protection where supported;
- use idempotency/deduplication;
- apply bounded processing;
- record relevant audit information;
- reject malformed or unauthorized requests.

Webhook receipt must not itself imply that the underlying business operation succeeded; the verified provider event must be interpreted according to its contract.

## 13. API Security

All externally reachable APIs must enforce:

- authentication where required;
- authorization;
- schema validation;
- request-size limits;
- rate limiting;
- safe error responses;
- timeout policies;
- content-type validation;
- path/query parameter validation.

API responses must use explicit DTOs and must not expose internal domain or persistence structures accidentally.

## 14. Input and Output Security

All external input is untrusted.

Validation must occur at the boundary and again inside domain/application logic where invariants require it.

The system must protect against common classes of abuse including:

- injection;
- path traversal;
- malformed serialization;
- oversized payloads;
- unsafe redirects;
- SSRF;
- prototype/object manipulation where relevant;
- authorization bypass;
- resource exhaustion.

Errors returned to clients must not reveal stack traces, credentials, internal topology, SQL statements, or sensitive implementation details.

## 15. Database Security

Applications access data through approved repositories/data-access boundaries.

Database credentials must follow least privilege.

Production services should not share unrestricted administrative database credentials.

Cross-domain direct table access is prohibited unless explicitly defined as infrastructure-level functionality rather than business communication.

Database backups must be protected with equivalent security controls.

## 16. Event and Message Security

Events and commands are trusted only according to their authenticated producer and validated contract.

Consumers must validate:

- event type;
- schema/version;
- producer identity where required;
- authorization context where applicable;
- payload integrity.

Sensitive information should not be placed into events unless consumers have a legitimate need for it.

Event logs and dead-letter queues must be treated as potentially sensitive data stores.

## 17. AI Security and Trust

AI agents are untrusted decision-making components unless and until a specific capability grants them authority.

AI agents must not receive unrestricted access to:

- databases;
- payment systems;
- identity systems;
- infrastructure;
- secrets;
- arbitrary network destinations.

AI actions are executed through governed capabilities/tools with explicit permissions.

High-impact actions require the human-in-the-loop controls defined by the AI and governance architecture.

AI-generated content is not automatically treated as authoritative system state.

## 18. Prompt and Tool Security

AI-facing inputs must be treated as untrusted content.

The system must defend against prompt injection and malicious instructions attempting to override system policies or tool permissions.

Tool authorization is evaluated independently of the model's requested action.

A model cannot grant itself additional permissions through generated text.

## 19. WhatsApp and External Channel Security

External messaging channels are untrusted interaction boundaries.

A WhatsApp message must be associated with an authenticated/verified platform identity before privileged account operations are executed.

Sensitive operations may require additional verification depending on risk.

The channel adapter must not bypass normal domain authorization simply because a request originated from a recognized phone number or external provider.

## 20. Anti-Replication and Intellectual Property Protection

Client applications are inherently inspectable. Security therefore focuses on protecting the platform's valuable server-side capabilities.

Sensitive algorithms and proprietary decision logic should remain server-side, including where applicable:

- pricing intelligence;
- recommendation/ranking logic;
- inventory optimization;
- fraud/risk models;
- AI orchestration policies;
- enterprise optimization logic.

Client-side obfuscation may raise reverse-engineering cost but is not treated as a primary security boundary.

## 21. Auditability

Security-relevant actions should produce auditable records sufficient to answer:

- who acted;
- what capability was used;
- what resource was affected;
- when it happened;
- through which channel;
- under which authorization context;
- what outcome occurred.

Audit records must avoid unnecessary sensitive payload retention.

## 22. Logging Security

Logs are operational data and may contain sensitive information.

Logging must therefore:

- avoid passwords, tokens and secrets;
- minimize personal data;
- protect log access;
- define retention;
- support correlation IDs;
- preserve security-relevant events;
- prevent attacker-controlled values from corrupting log interpretation.

## 23. Security Headers and Transport

Public HTTP services must use secure transport and appropriate HTTP security controls.

TLS certificates and keys must be managed outside application source code.

Where applicable, APIs should use security headers and restrictive cross-origin policies appropriate to their clients.

## 24. Rate Limiting and Abuse Controls

Security controls must distinguish ordinary workload from abusive workload.

Controls may include:

- IP-based limits;
- identity-based limits;
- endpoint-specific limits;
- account lockouts or progressive challenges;
- concurrency limits;
- queue backpressure.

Rate limits must not create an authorization bypass or denial-of-service vulnerability through unbounded trusted identities.

## 25. Dependency and Supply-Chain Security

Dependencies are part of the platform's trust boundary.

The project should maintain:

- dependency review;
- lockfiles;
- vulnerability scanning;
- controlled upgrade processes;
- provenance where available;
- minimized production dependencies.

Build and deployment systems must not execute arbitrary untrusted code with production credentials.

## 26. Production Configuration

Production configuration must be explicit and fail closed.

Examples of unsafe behaviour include:

- silently enabling development authentication;
- accepting missing security configuration with permissive defaults;
- using development credentials in production;
- exposing debug endpoints;
- returning verbose internal errors.

Configuration validation belongs at startup where possible so invalid security posture prevents deployment or process startup.

## 27. Incident Response

The architecture must support:

- credential revocation;
- secret rotation;
- session invalidation;
- service isolation;
- event replay/recovery;
- forensic audit review;
- controlled rollback;
- emergency configuration changes.

Security incidents must be observable without requiring access to application source or database internals.

## 28. Rules

1. All external input is untrusted.
2. Authentication and authorization remain separate concerns.
3. Authorization is enforced by resource-owning services.
4. Ownership must be enforced at the data-access boundary where possible.
5. Production security configuration fails closed.
6. Secrets never belong in source control.
7. Service identities use least privilege.
8. Client-controlled identity and ownership fields are never authoritative.
9. Payment state changes require verified provider evidence where applicable.
10. Webhooks require authentication, validation and idempotent handling.
11. AI agents operate through governed capabilities.
12. AI-generated instructions cannot grant permissions.
13. External channels cannot bypass domain authorization.
14. Sensitive business logic remains server-side.
15. Security-relevant operations are observable and auditable.
16. Security controls must survive retries, duplicate messages and partial failures.
17. Security architecture must preserve the domain and aggregate boundaries established in Phase 2.

## 29. Phase 3.10 Exit Criteria

Phase 3.10 is complete when:

- trust boundaries are explicit;
- authentication and authorization responsibilities are defined;
- service identity is defined;
- secret handling and rotation requirements are defined;
- resource ownership enforcement is explicit;
- API, database, event and webhook security rules are defined;
- payment security boundaries are defined;
- AI capability security is defined;
- external channel security is defined;
- anti-replication protection boundaries are defined;
- audit and logging security requirements are defined;
- dependency/supply-chain controls are defined;
- production configuration fails closed;
- incident-response capabilities are architecturally supported.
