# Phase 3.12 — API & Service Architecture

## Status

Accepted

## Purpose

Define how Essentials Mart backend services expose capabilities, communicate across domain boundaries, enforce contracts, and evolve without coupling the enterprise model to transport technology.

## Architectural Principles

1. Domain ownership remains authoritative over its own state.
2. APIs expose capabilities, not database tables.
3. Services enforce domain invariants; clients never bypass them.
4. Synchronous calls are used where an immediate answer is required.
5. Events are used for durable cross-domain reactions and eventual consistency.
6. External integrations are isolated behind adapters.
7. Every mutating request is authenticated, authorized, validated, and observable.
8. API contracts are versioned deliberately and remain backward compatible during migration.
9. Idempotency is mandatory for retryable commands with financial or state-changing effects.
10. Internal implementation details, database schemas, and proprietary intelligence remain private to their owning boundary.

## Service Boundary Model

Services are organized around enterprise domains and capabilities rather than UI screens.

A service may own:

- application orchestration,
- domain commands,
- domain queries/read models,
- persistence adapters,
- domain events,
- integration adapters.

A service must not directly mutate another service's database or bypass its domain API.

## API Styles

### Synchronous APIs

HTTP/JSON APIs are the default synchronous interface for client-facing and suitable internal request/response operations.

Use synchronous APIs for:

- authentication/session operations,
- product queries,
- cart operations,
- checkout commands requiring immediate acknowledgement,
- order queries,
- user-facing status requests.

### Asynchronous APIs

Events and commands over the enterprise event infrastructure are used when work can continue independently or when multiple consumers must react to a fact.

Use asynchronous communication for:

- inventory reservation and release,
- payment webhook processing,
- notifications,
- fulfilment progression,
- analytics projections,
- AI intelligence reactions,
- enterprise integration workflows.

## Command vs Query Separation

Commands change state and must have explicit authorization, validation, idempotency and audit semantics.

Queries must not mutate authoritative state. Read models may be optimized independently from transactional storage.

Examples:

- `POST /basket/items` — command
- `DELETE /basket/items/{productId}` — command
- `POST /checkout` — command
- `GET /products/{id}` — query
- `GET /orders/{id}` — query

## API Contract Requirements

Every public API contract should define:

- method and path,
- authentication requirements,
- authorization requirements,
- request schema,
- response schema,
- error contract,
- idempotency semantics where applicable,
- pagination/filtering rules where applicable,
- rate limits where applicable,
- audit requirements,
- compatibility expectations.

Public response DTOs must be explicitly mapped. Domain objects must never be serialized directly as an accidental API contract.

## Error Contract

API errors use stable machine-readable codes and human-readable messages.

The machine-readable code determines protocol behavior; message wording may change without changing API semantics.

Errors should distinguish at least:

- authentication failure,
- authorization failure,
- validation failure,
- resource not found,
- conflict/stale state,
- rate limiting,
- unsupported media/request,
- payload limits,
- dependency failure,
- internal failure.

Internal stack traces, database errors, secrets, and proprietary reasoning must not be returned to clients.

## Resource Ownership

Every resource lookup must enforce ownership at the repository/service boundary where appropriate.

For customer-scoped resources, the preferred pattern is a scoped lookup such as:

`getOwnedById(customerId, resourceId)`

rather than retrieving an arbitrary resource and filtering it afterward.

This reduces enumeration risk and establishes the correct boundary for future database implementations.

## Idempotency

Retryable state-changing operations must support idempotency where duplicate execution could create financial, fulfillment, or other material side effects.

Examples include:

- checkout,
- payment initiation,
- refund creation,
- inventory reservation,
- delivery creation,
- notification dispatch where duplicate delivery matters.

Idempotency records must be scoped to the authenticated principal and operation semantics.

## Authentication & Authorization

Authentication establishes identity. Authorization determines whether that identity may perform the requested operation.

Authorization must be enforced server-side and must not depend on client UI state.

Privileged service-to-service operations use explicit service identities and least-privilege permissions.

## Cross-Domain Communication

A service may reference another domain by stable identifier and consume its published contract. It must not assume ownership of another domain's state.

Example:

`Commerce -> ProductId -> Product capability/read model`

Commerce may snapshot product information into an OrderItem, but Commerce does not mutate Product state.

## Events

Events represent facts that have occurred. Event names and payloads must follow the authoritative enterprise event vocabulary established in the architecture corpus.

Event consumers must be:

- idempotent,
- observable,
- resilient to retries,
- tolerant of event reordering where the contract permits it,
- explicit about version compatibility.

The transactional outbox pattern should be used where an authoritative state change and publication of its event must remain reliably coordinated.

## External Integrations

Payment providers, WhatsApp, delivery providers, identity providers, maps, messaging systems, and other external systems are integration boundaries.

External provider APIs must be accessed through adapters so provider-specific protocols do not leak into domain logic.

Webhook endpoints must validate authenticity, enforce idempotency, and treat provider notifications as untrusted input until verified.

## AI Integration

AI agents do not receive unrestricted database access merely because they participate in a workflow.

AI interactions must pass through explicit capabilities/tools with:

- authorization,
- input validation,
- scope restrictions,
- auditability,
- rate controls,
- deterministic business-rule enforcement where required.

AI-generated recommendations must not bypass authoritative service commands.

## Client Integration

Flutter and future clients consume stable API contracts rather than internal service implementations.

The client must not encode authoritative pricing, inventory, authorization, payment, or fulfillment rules as its source of truth.

The same backend contracts must support app, WhatsApp and other approved channels where capabilities overlap.

## API Evolution

Compatible changes should be preferred over unnecessary version proliferation.

Backward-compatible changes include adding optional response fields and optional request capabilities where semantics remain unchanged.

Breaking changes require an explicit versioning and migration strategy.

Deprecated endpoints must have a documented removal path and observable usage before retirement.

## Resilience

Services must assume dependencies can fail.

Required patterns include:

- bounded timeouts,
- controlled retries,
- exponential backoff where appropriate,
- circuit breaking where justified,
- idempotent retry semantics,
- graceful degradation for non-critical dependencies,
- dead-letter handling for failed asynchronous work.

Retries must never turn a transient failure into duplicated financial or fulfillment actions.

## Observability

Every request and asynchronous operation should be traceable through a correlation/trace identifier.

Operational telemetry should capture:

- request latency,
- status/error code,
- dependency latency,
- retry activity,
- queue/event processing state,
- authorization outcomes,
- business transaction identifiers where appropriate.

Sensitive personal, financial, authentication, and secret material must not be logged.

## Security Boundary

API gateways, service boundaries, authorization middleware, domain services, repositories, and external adapters form layered controls.

No single client-side control is considered sufficient for security.

## Relationship to Earlier Architecture

This architecture implements the enterprise domain, aggregate, event, security, persistence, observability, AI Society, and intelligence-engine boundaries established in Phase 1 and Phase 2.

It is specifically constrained by:

- domain ownership,
- aggregate consistency boundaries,
- authoritative event vocabulary,
- explicit security policies,
- persistence ownership,
- AI capability governance.

## Acceptance Criteria

Phase 3.12 is complete when:

- service boundaries map to enterprise ownership,
- synchronous and asynchronous communication rules are explicit,
- API contracts are explicit and versionable,
- errors use stable codes,
- ownership is enforced server-side,
- idempotency requirements are defined,
- external integrations are isolated,
- AI access is capability-based,
- observability and resilience requirements are defined,
- no API contract exposes internal domain objects accidentally.
