# Phase 3.8 — Deployment & Environment Architecture

**Status:** Accepted  
**Phase:** 3 — Backend Architecture  
**Depends on:** Enterprise Architecture, EIP, ADRs, Phase 2 Information Architecture, Phase 3.1–3.7

## 1. Purpose

Define how Essentials Mart is built, configured, deployed, promoted, operated, and isolated across environments without weakening the architectural boundaries established by the enterprise model.

## 2. Environment Model

Essentials Mart shall maintain explicit environment boundaries:

- **Local** — developer execution using safe development fixtures and local infrastructure.
- **Development** — shared integration environment for active engineering work.
- **Staging** — production-like validation environment.
- **Production** — live customer and enterprise workloads.

Each environment has its own configuration, credentials, data stores, event infrastructure, observability resources, and external integrations unless an explicitly documented exception exists.

Production data must never be copied into lower environments by default.

## 3. Configuration

Application behaviour that varies by environment must be configuration-driven rather than hard-coded into domain logic.

Configuration shall:

- be injected at the composition/deployment boundary;
- be validated at startup;
- distinguish required secrets from ordinary configuration;
- fail closed when security-sensitive configuration is invalid;
- never expose secrets to client applications;
- avoid environment-variable reads inside domain entities and business rules.

Development conveniences must have explicit opt-in semantics and must not weaken production security.

## 4. Secrets

Secrets are deployment concerns, not source-code concerns.

Secrets must:

- never be committed to Git;
- be stored in an appropriate secret-management system;
- be scoped to the environment and service that needs them;
- be rotated without requiring domain-code changes;
- be excluded from logs, telemetry, client bundles, and error responses.

## 5. Build and Artifact Strategy

Builds must produce immutable, identifiable artifacts.

The preferred promotion model is:

```text
Source
  ↓
CI validation
  ↓
Build
  ↓
Immutable artifact
  ↓
Staging
  ↓
Verification
  ↓
Production
```

The same validated artifact should be promoted between environments rather than rebuilding different application code for production.

## 6. Deployment Boundaries

Services are independently deployable where domain ownership and operational requirements justify it.

A deployment must not bypass architectural boundaries by directly manipulating another domain's database. Cross-domain interaction occurs through the approved API, command, event, or read-model boundary.

Database migrations are versioned artifacts and must be compatible with the deployment strategy.

## 7. Database and Persistence Deployment

Each production persistence boundary must have:

- controlled credentials;
- migration history;
- backup and recovery procedures;
- monitoring;
- access auditing;
- defined ownership.

Schema changes should use an expand-and-contract approach when zero-downtime deployment requires compatibility across application versions.

## 8. Event Infrastructure

Event infrastructure is environment-isolated.

Events from development or staging must never accidentally reach production consumers.

Consumers must be designed for:

- duplicate delivery;
- retries;
- delayed delivery;
- poison messages;
- idempotent processing;
- dead-letter handling.

## 9. External Integrations

External providers such as payment gateways, messaging providers, WhatsApp infrastructure, maps, AI providers, and delivery services must be explicitly configured per environment.

Sandbox/test credentials must be used outside production whenever providers support them.

Production credentials must never be reused in local, development, or staging environments.

## 10. CI/CD Governance

The delivery pipeline should enforce, at minimum:

1. formatting/lint validation where configured;
2. type checking;
3. unit tests;
4. integration/API tests;
5. architecture/documentation consistency checks where applicable;
6. security and dependency checks;
7. build verification;
8. deployment health checks.

Production deployment should require successful validation of the artifact being promoted.

## 11. Rollback and Recovery

Every production deployment must have a defined recovery path.

Rollback strategy depends on the change type:

- application-only changes may roll back to a previous immutable artifact;
- compatible schema changes may roll back the application independently;
- destructive schema changes require a forward-recovery strategy rather than assuming database rollback is safe;
- event-driven changes must account for already-published events and consumer versions.

Recovery procedures must be tested rather than merely documented.

## 12. Availability and Scaling

Runtime infrastructure must support horizontal scaling where required.

Application instances should remain stateless wherever practical. Durable state belongs in the appropriate persistence or infrastructure boundary.

Scaling decisions must preserve aggregate ownership, transactional boundaries, event semantics, and idempotency guarantees established in earlier architecture phases.

## 13. Observability

Every deployed service must expose sufficient operational signals to determine:

- whether it is healthy;
- which version is running;
- which environment it belongs to;
- whether dependencies are available;
- whether requests/events are failing;
- whether latency or resource usage is abnormal.

Logs, metrics, traces, and audit records must follow the observability and trust architecture already established for Essentials Mart.

## 14. Security Boundary

Production deployment must fail closed when required security configuration is absent or contradictory.

Development authentication shortcuts, fixtures, test gateways, debug routes, and development-only capabilities must not become available in production merely because a configuration variable was omitted or misconfigured.

Client applications are never trusted as deployment or security boundaries.

## 15. Data Protection

Production data must be protected in transit and at rest according to the security architecture.

Backups must be encrypted, access-controlled, monitored, and periodically restored in a controlled environment to verify recoverability.

Personally identifiable, financial, household, and AI-related data must follow the applicable retention and access policies.

## 16. Infrastructure as Code

Infrastructure configuration should be version-controlled and reproducible where practical.

Manual production changes must be exceptional, auditable, and subsequently reconciled into the authoritative infrastructure configuration.

## 17. Deployment Metadata

Every deployed artifact should expose or record:

- application/service name;
- version or commit identifier;
- build timestamp;
- deployment environment;
- configuration/schema version where relevant.

This metadata supports incident response, auditability, and rollback.

## 18. Architecture Rules

1. Production is isolated from all non-production environments.
2. Secrets never belong in source code or client bundles.
3. Environment configuration belongs at composition/deployment boundaries.
4. Domain logic must not depend directly on deployment environment variables.
5. Production deployments use validated, identifiable artifacts.
6. Cross-domain database access is prohibited unless explicitly authorised by the architecture.
7. Events are environment-isolated and consumers are idempotent.
8. Production external integrations require explicit production configuration.
9. Database migrations are versioned and deployment-aware.
10. Every production change has a recovery strategy.
11. Operational visibility is part of the deployment contract, not an afterthought.
12. Development conveniences must never silently weaken production security.

## 19. Relationship to Earlier Architecture

This document implements the deployment implications of the enterprise and backend architecture. It does not redefine domain ownership, aggregate boundaries, API contracts, AI authority, persistence ownership, or observability policy.

Where deployment concerns intersect those boundaries, the earlier authoritative architecture remains the source of truth.

## 20. Phase 3.8 Exit Criteria

Phase 3.8 is complete when:

- environment boundaries are defined;
- configuration and secret ownership is explicit;
- build and artifact promotion is defined;
- CI/CD gates are defined;
- database and event deployment boundaries are defined;
- external integration isolation is defined;
- rollback and recovery principles are defined;
- production security fail-closed behaviour is defined;
- observability and deployment metadata requirements are defined.
