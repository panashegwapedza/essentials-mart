# Essentials Mart — Data, Storage & Persistence Architecture

**Status:** Defined — Phase 3.11  
**Phase:** 3 — Backend Architecture

## Purpose

This document defines how Essentials Mart stores, retrieves, protects, replicates, archives and deletes data across its persistence landscape.

It complements, rather than replaces, the logical database architecture in `3.1-DATABASE-ARCHITECTURE.md` and the physical schema specification in `3.2-PHYSICAL-DATABASE-SCHEMA-SPECIFICATION.md`.

The architecture preserves the Phase 2 information model and aggregate ownership. Storage technology must serve those boundaries rather than redefine them.

## 1. Persistence Principles

1. Authoritative state has one clear persistence owner.
2. Aggregate boundaries remain the primary transactional consistency boundary.
3. Storage implementations must not create accidental cross-domain coupling.
4. Operational databases, event infrastructure, object storage, caches and analytical stores have distinct responsibilities.
5. Authoritative records must be durable before a workflow claims the corresponding state transition is committed.
6. Derived data must be reconstructible or explicitly classified as non-reconstructible.
7. Historical financial, audit and transactional records are retained according to their lifecycle and compliance requirements.
8. Deletes must respect legal, security, audit and referential requirements.
9. Backups are not substitutes for replication, and replication is not a substitute for backups.
10. Recovery objectives must be defined per data class rather than assumed to be identical across the platform.
11. Encryption, authorization and tenant/ownership isolation apply to every persistence mechanism, not only the primary database.
12. Storage decisions must remain portable enough to permit future service/database separation without changing domain ownership.

## 2. Storage Landscape

Essentials Mart uses a polyglot persistence model only where the access pattern and lifecycle justify it.

```text
                    ┌─────────────────────────┐
                    │   Domain Services       │
                    └────────────┬────────────┘
                                 │
             ┌───────────────────┼───────────────────┐
             │                   │                   │
             ▼                   ▼                   ▼
      ┌─────────────┐     ┌──────────────┐    ┌──────────────┐
      │ PostgreSQL  │     │ Event Store/ │    │ Object       │
      │ Operational │     │ Event Bus    │    │ Storage      │
      │ State       │     │              │    │              │
      └─────────────┘     └──────────────┘    └──────────────┘
             │                   │                   │
             └───────────────────┼───────────────────┘
                                 │
                 ┌───────────────┴───────────────┐
                 │                               │
                 ▼                               ▼
          ┌──────────────┐                ┌──────────────┐
          │ Read Models  │                │ Analytics /  │
          │ & Caches     │                │ Intelligence │
          └──────────────┘                └──────────────┘
```

### Primary relational storage

PostgreSQL/Supabase is the initial authoritative operational persistence platform.

It stores domain-owned transactional state according to the schemas defined in Phase 3.2.

### Event infrastructure

Events provide durable integration between independently owned domains. Event infrastructure is not a replacement for authoritative domain state.

### Object storage

Object storage is used for large or binary artefacts such as:

- product media;
- store-layout assets where appropriate;
- delivery documents;
- exports;
- AI artefacts requiring object persistence;
- operational attachments.

Large binary payloads must not be embedded unnecessarily in transactional rows.

### Read models and caches

Read models and caches optimise access without becoming alternate sources of truth.

A cache may always be discarded and reconstructed from authoritative state or an authoritative projection source.

### Analytical storage

Enterprise intelligence, forecasting and historical analysis may use analytical projections optimized for scans and aggregation. Analytical copies do not acquire transactional authority.

## 3. Authoritative vs Derived Data

Every persisted dataset must be classified as one of:

| Class | Meaning | Recovery expectation |
|---|---|---|
| Authoritative | Source of truth for a domain state | Must be durably recoverable |
| Event | Durable fact used for integration/audit | Must be durably recoverable according to event retention |
| Projection | Rebuildable derived representation | Rebuild from authoritative source/events |
| Cache | Disposable performance representation | May be discarded |
| Analytical | Derived historical/aggregate representation | Rebuild or restore according to analytical requirements |
| AI-derived | Recommendation, embedding, forecast, working memory or decision artefact | Lifecycle and provenance explicitly defined |
| Binary artefact | Large object referenced by domain records | Retention tied to owning entity/lifecycle |

The classification must be explicit in the implementation and documentation for new persistence stores.

## 4. Transactional Persistence

Writes that change authoritative aggregate state must execute within the owning persistence boundary.

Examples include:

- Cart mutation;
- Checkout state transition;
- Order creation;
- Payment transaction transition;
- Refund transition;
- Inventory reservation transition;
- Fulfilment transition;
- Delivery transition.

A service must not partially persist an aggregate and then report success before the authoritative transaction is committed.

Cross-domain workflows use events or explicit commands rather than distributed database transactions wherever practical.

## 5. Idempotency and Duplicate Delivery

Persistence must assume that distributed commands, events and webhooks may be delivered more than once.

Where an operation has externally visible side effects, the owning boundary must define an idempotency key or equivalent deduplication identity.

Examples:

- payment provider callbacks;
- order creation commands;
- inventory reservation requests;
- notification delivery attempts;
- event consumers.

Idempotency records must have a defined scope, retention period and ownership boundary.

## 6. Concurrency and Consistency

The platform uses strong consistency inside aggregate boundaries and eventual consistency between independent boundaries unless an explicit architecture decision requires otherwise.

Concurrency controls may include:

- optimistic version checks;
- database transactions;
- unique constraints;
- conditional updates;
- reservation locks;
- idempotency keys.

A concurrency mechanism must protect an actual invariant. It must not merely create the appearance of safety.

For high-contention resources such as inventory, the physical implementation must ensure that competing reservations cannot consume the same available quantity beyond the permitted invariant.

## 7. Connection and Resource Management

Backend services must treat database connections and other storage resources as finite infrastructure.

Requirements:

- use connection pooling appropriate to deployment topology;
- avoid opening a new database connection for every request;
- configure bounded pool sizes;
- apply statement/query timeouts where appropriate;
- release transactions and connections deterministically;
- monitor pool saturation;
- prevent unbounded concurrent storage operations.

Serverless or autoscaled deployments must account for connection amplification and use a pooling strategy compatible with the selected database platform.

## 8. Indexing and Query Design

Indexes must be driven by authoritative access patterns documented by each service.

Required principles:

- every index must support a known query or integrity constraint;
- avoid speculative index proliferation;
- composite indexes must reflect actual filter/order patterns;
- ownership-scoped queries must include the ownership key where applicable;
- time-series queries must consider timestamp indexing and retention;
- indexes must be reviewed as data volume grows.

Queries must retrieve only the data required for the operation or response. API DTO boundaries must remain independent from persistence row shape.

## 9. Read Models and Cache Invalidation

Read models may combine information from multiple domains for experiences such as:

- customer dashboards;
- order history;
- household views;
- Walk Mode;
- inventory availability;
- recommendations;
- enterprise intelligence.

A projection update may lag the authoritative transaction. Consumers must therefore understand its consistency semantics.

Caches must have:

- an explicit owner;
- a defined key structure;
- TTL/invalidation policy;
- bounded size where appropriate;
- a documented fallback to authoritative data.

A cache miss must never change business correctness.

## 10. Event Persistence and the Transactional Outbox

When a domain transaction changes authoritative state and requires an event to be published, the implementation should use a transactional outbox or equivalent atomic persistence mechanism.

Conceptually:

```text
Domain transaction
      │
      ├── authoritative state change
      │
      └── outbox event record
                │
                ▼
          Event publisher
                │
                ▼
           Event bus
```

This prevents the failure mode where database state commits but the corresponding integration event is lost.

Event publication must be retryable and idempotent. Consumers must also be idempotent because delivery may occur more than once.

## 11. Backup Strategy

Authoritative operational data requires backups independent of the live database.

The backup strategy must provide:

- automated scheduled backups;
- point-in-time recovery where supported and justified;
- encrypted backup storage;
- retention periods appropriate to data classification;
- access controls separate from ordinary application credentials;
- monitoring of backup success/failure;
- periodic restoration tests.

A backup that has never been successfully restored must not be treated as a proven recovery mechanism.

## 12. Replication and High Availability

Replication is used to improve availability and read scalability where justified.

The architecture distinguishes:

- primary/authoritative write state;
- synchronous or strongly consistent replicas where required;
- asynchronous read replicas;
- disaster-recovery replicas.

Applications must understand replica lag. A workflow that requires read-after-write consistency must read from the authoritative consistency boundary rather than assuming every replica is immediately current.

Replication must never create multiple authorities for the same aggregate.

## 13. Disaster Recovery

Recovery planning is defined using two measures:

- **RPO — Recovery Point Objective:** maximum acceptable data loss window;
- **RTO — Recovery Time Objective:** maximum acceptable service restoration window.

Initial priority classification:

| Data/Capability | Priority | Principle |
|---|---|---|
| Identity/authentication | Critical | Restore securely and quickly |
| Orders | Critical | Preserve transactional history |
| Payments/refunds | Critical | Preserve financial records and auditability |
| Inventory | Critical | Restore authoritative stock state |
| Cart | High | Recover where practical; user-facing temporary state may be reconstructible |
| Fulfilment/delivery | Critical | Preserve active operational workflows |
| Notifications | Medium/High | Delivery state must remain auditable |
| AI working memory | Medium | Reconstruct where possible |
| Caches | Low | Rebuild |
| Analytical projections | Medium | Rebuild or restore from governed source |

Concrete RPO/RTO targets must be established during production capacity and operations planning rather than invented as architectural guarantees prematurely.

## 14. Data Lifecycle and Retention

Persistence follows the lifecycle defined for each entity in Phase 2.

Lifecycle operations include:

```text
Create
  ↓
Active
  ↓
Updated / Transitioned
  ↓
Archived (where applicable)
  ↓
Deleted / Anonymised (where permitted)
```

Retention rules must distinguish:

- operational convenience;
- contractual obligations;
- financial/legal retention;
- security/audit retention;
- privacy requirements;
- AI-derived data retention.

No generic global deletion policy may override a domain-specific retention requirement.

## 15. Deletion, Anonymisation and Legal Holds

Deletion is an explicit domain operation, not merely a SQL `DELETE`.

Where an identity must be removed while historical financial records must remain, the implementation may use controlled anonymisation or pseudonymisation while preserving required transactional integrity.

Legal or regulatory holds must prevent eligible records from being physically deleted until the hold is released.

Audit records must not be altered merely to satisfy an operational deletion request unless the governing retention/privacy policy explicitly permits it.

## 16. Encryption and Sensitive Storage

Data must be protected in transit and at rest using platform-supported encryption controls.

Secrets such as passwords, authentication credentials, private keys and provider secrets must not be stored as ordinary application data.

Payment-sensitive information must follow the selected PSP's security model and should minimise storage of sensitive payment credentials inside Essentials Mart systems.

Encryption keys and application secrets must be managed outside source control and rotated according to operational policy.

## 17. Multi-Store and Future Distribution

The initial relational deployment may remain physically centralised while the logical model remains domain- and store-aware.

Store-scoped operational data must carry an authoritative `StoreId` or equivalent context where required.

Future horizontal partitioning, sharding or database-per-service strategies must preserve:

- aggregate ownership;
- stable IDs;
- event contracts;
- API boundaries;
- auditability;
- cross-store isolation.

The architecture must not prematurely shard data merely because the platform is intended to scale globally.

## 18. AI and Derived Storage

AI Society may use specialised stores for:

- embeddings/vector representations;
- recommendation artefacts;
- forecasts;
- behavioural signals;
- agent working memory;
- decision traces.

These stores remain subordinate to the authoritative domain model.

AI data must carry sufficient provenance to answer:

- what generated it;
- from which source/context;
- when it was generated;
- which model/agent/capability was involved;
- what retention policy applies.

An AI store must never silently become the source of truth for Customer, Order, Payment, Inventory or other operational aggregates.

## 19. Observability

Persistence infrastructure must expose metrics and logs for at least:

- query latency;
- transaction latency;
- error rates;
- connection-pool utilisation;
- deadlocks/contention;
- replication lag;
- storage capacity;
- cache hit/miss behaviour;
- event/outbox backlog;
- backup success/failure;
- restore-test results.

Logs must avoid exposing secrets or unnecessary sensitive data.

Storage incidents must carry correlation identifiers so they can be connected to the application and audit trail where appropriate.

## 20. Security Boundaries

Database roles, service credentials and storage permissions must follow domain ownership and least privilege.

A service should receive write access only to persistence it owns.

Cross-domain read access must be deliberate and preferably mediated through:

- service APIs;
- governed read models;
- event projections;
- explicit database roles where a shared database is temporarily necessary.

Row-level security, where used, must enforce actual authorization and ownership invariants rather than simply mirror frontend visibility.

## 21. Migration and Schema Evolution

Persistence changes must be forward-compatible with the running system wherever rolling deployment requires it.

Preferred sequence:

```text
Expand
  ↓
Deploy compatible application
  ↓
Backfill / migrate
  ↓
Switch reads/writes
  ↓
Contract old structure
```

Destructive schema changes require explicit review, backup/recovery confidence and confirmation that no active consumer depends on the old structure.

Database migrations must not silently redefine aggregate ownership or public API contracts.

## 22. Testing Requirements

Persistence implementations must be tested at multiple levels:

### Unit tests

Verify domain invariants independently of the storage technology.

### Integration tests

Verify:

- transaction boundaries;
- constraints;
- ownership enforcement;
- concurrency behaviour;
- idempotency;
- event/outbox persistence;
- migration correctness.

### Recovery tests

Verify that backups and disaster-recovery procedures can actually restore required data and service state.

### Load tests

Verify behaviour under realistic query rates, connection pressure, contention and data volume.

Tests must not claim production guarantees that the selected development adapter cannot provide.

## 23. Technology Evolution

The initial implementation may use PostgreSQL/Supabase as the principal relational store, with supporting infrastructure selected according to actual requirements.

Technology may evolve toward:

- separate databases per domain;
- read replicas;
- dedicated analytical storage;
- vector storage;
- specialised object storage;
- regional data stores;
- partitioned or sharded persistence.

Such evolution must preserve the logical architecture. Changing storage technology is an implementation decision; changing ownership, aggregate boundaries or authoritative semantics is an architectural decision requiring the appropriate ADR/EIP process.

## 24. Phase 3.11 Exit Criteria

Phase 3.11 is complete when the implementation team can answer, for every persistence class:

1. What is authoritative?
2. Who owns it?
3. Where is it stored?
4. How is it transactionally written?
5. How is it read and cached?
6. How is it replicated?
7. How is it backed up?
8. How is it restored?
9. How long is it retained?
10. How is it deleted or anonymised?
11. How is it secured?
12. How is it observed?
13. How does it evolve without breaking active consumers?
14. How is the data recovered after a failure?

The answers must remain consistent with Phase 2, Phase 3.1, Phase 3.2, the EDA, ADRs and EIPs.
