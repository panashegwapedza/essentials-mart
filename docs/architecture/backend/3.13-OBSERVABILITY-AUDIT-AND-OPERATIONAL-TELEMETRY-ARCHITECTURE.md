# Essentials Mart — Backend Observability, Audit & Operational Telemetry Architecture

**Phase:** 3.13 — Backend Architecture  
**Status:** Proposed  
**Date:** 2026-08-23  
**Authority:** ADR-016, ADR-004, ADR-003, ADR-015, ADR-018  

## 1. Purpose

This document defines the backend observability architecture for Essentials Mart.

Observability is a platform capability, not an afterthought. Every important request, command, event, integration, AI-assisted action and material state transition must produce sufficient evidence to understand what happened, why it happened, who or what initiated it, and what the system subsequently did.

The architecture distinguishes:

- operational telemetry;
- security telemetry;
- business and domain audit evidence;
- AI decision evidence;
- distributed tracing;
- metrics;
- structured logs;
- event and message telemetry; and
- incident evidence.

This document does not replace ADR-016. It translates its observability and trust requirements into backend implementation boundaries.

## 2. Architectural Principles

1. **Observable by construction** — material backend operations must emit or expose diagnostic evidence as part of their design.
2. **Audit is not logging** — audit evidence is durable, structured and governed; ordinary logs are operational diagnostics.
3. **Correlation is mandatory** — related requests, commands, events, jobs and external calls must be correlatable.
4. **Domain ownership is preserved** — services emit evidence about their own state and actions without becoming owners of another domain's data.
5. **Evidence is append-oriented** — historical audit records must not be silently rewritten.
6. **Sensitive data minimisation** — telemetry must never become an uncontrolled copy of customer, payment, credential or proprietary data.
7. **Failure is observable** — errors, retries, timeouts, rejected commands and degraded dependencies must be diagnosable.
8. **AI actions are attributable** — an AI-originated action must be distinguishable from a human action and linked to its governing authority and decision context.
9. **External dependencies are observable at the boundary** — provider calls must expose latency, outcome, retries and correlation without leaking provider internals into core domains.
10. **Telemetry must remain useful at scale** — collection, retention and cardinality must be governed.

## 3. Observability Model

Essentials Mart uses four complementary evidence layers:

| Layer | Purpose | Examples |
|---|---|---|
| Logs | Diagnostic narrative | request failure, validation failure, dependency timeout |
| Metrics | Aggregated system health | latency, throughput, error rate, queue depth |
| Traces | End-to-end causal path | HTTP request → service → event → worker → provider |
| Audit evidence | Durable accountability | order state change, authorisation decision, AI action, refund approval |

No single layer is considered sufficient for critical operations.

## 4. Correlation Context

Every externally initiated request must establish or accept a correlation context under the platform's trust rules.

At minimum, the backend should support:

- `trace_id` — distributed execution trace;
- `request_id` — individual inbound request identity;
- `correlation_id` — business/process correlation across asynchronous boundaries;
- `causation_id` — identifier of the event or command that caused the current operation;
- `actor_id` — authenticated human, system or governed agent identity where applicable;
- `tenant_id` / enterprise scope where applicable;
- `service_name`; and
- environment/deployment identity.

Correlation identifiers must propagate through approved service, event and job boundaries.

## 5. Structured Logging

Backend services must emit structured logs rather than relying on free-form strings for machine analysis.

A production log record should support fields such as:

```text
 timestamp
 level
 service
 environment
 trace_id
 request_id
 correlation_id
 causation_id
 actor_type
 actor_id
 operation
 domain
 outcome
 error_code
 duration_ms
 dependency
 deployment_version
```

Sensitive values must be excluded or redacted according to the security and privacy policy.

Passwords, access tokens, payment credentials, full authentication headers, secrets and unnecessary personal data must never be written to logs.

## 6. Metrics

Services must expose metrics sufficient to detect degradation before users report it.

### Core service metrics

- request count;
- request latency;
- error count and rate;
- status-code distribution;
- dependency latency;
- dependency failure rate;
- timeout count;
- retry count;
- saturation/resource utilisation; and
- active requests/jobs where relevant.

### Domain metrics

Commerce and fulfilment services should additionally expose governed metrics such as:

- basket creation/update rate;
- checkout success/failure rate;
- order creation rate;
- payment transition outcomes;
- inventory reservation outcomes;
- fulfilment latency;
- delivery lifecycle latency; and
- notification delivery outcomes.

Domain metrics must be aggregated and must not expose unnecessary customer-level data.

## 7. Distributed Tracing

Tracing must follow the causal path of important synchronous and asynchronous operations.

Example:

```text
Client Request
    |
    v
API Gateway
    |
    v
Commerce Service
    |
    +--> Inventory Service
    |
    +--> Payment Service
    |
    +--> Event Bus
             |
             +--> Fulfilment
             +--> Notification
             +--> Audit
```

Trace propagation must remain intact across approved message and job boundaries.

Asynchronous consumers should create child spans or linked spans while retaining the originating correlation and causation context.

## 8. Audit Evidence

Audit records are authoritative evidence of material actions and state transitions.

Examples include:

- authentication and authorisation decisions;
- order creation and material state changes;
- payment state transitions;
- refund decisions;
- inventory reservation/release actions;
- administrative changes;
- AI capability invocation;
- AI authority decisions;
- human approval or rejection;
- Walk Mode autonomous actions; and
- external partner actions that materially affect platform state.

An audit record should identify:

```text
 audit_id
 timestamp
 actor
 actor_type
 action
 target_type
 target_id
 domain
 outcome
 reason/code
 correlation_id
 causation_id
 trace_id
 policy/version context where required
```

Audit records must be append-oriented and protected against unauthorised modification.

## 9. AI Observability

AI Society operations require additional evidence beyond ordinary service telemetry.

Where applicable, an AI action must be traceable to:

1. the requesting actor or system;
2. the participating agent;
3. the capability invoked;
4. the authority/policy decision;
5. the relevant Intelligence Engine;
6. the material input/context references;
7. the resulting recommendation or action;
8. whether human approval was required;
9. whether human approval was granted or rejected; and
10. the resulting domain operation.

Telemetry must not expose confidential prompts, proprietary model internals or sensitive household information unnecessarily.

The invariant remains:

> AI capability does not imply AI authority.

Observability must therefore make authority explicit rather than merely recording that an AI component ran.

## 10. Event and Message Observability

Every governed event should carry sufficient metadata to support operational diagnosis.

At minimum:

- event identifier;
- event type/version;
- occurred-at timestamp;
- producer;
- aggregate/entity reference where appropriate;
- correlation identifier;
- causation identifier;
- trace context;
- schema/version metadata; and
- delivery/processing metadata where supplied by infrastructure.

Consumers should record failures, retries, dead-letter transitions and processing latency without modifying the event's authoritative business payload.

## 11. External Integration Observability

External partner calls must be observable at the integration boundary.

Record:

- provider/adapter identity;
- operation;
- request correlation;
- latency;
- timeout/failure classification;
- retry count;
- final outcome;
- circuit-breaker/degradation state where applicable; and
- provider reference identifiers when safe to retain.

Provider-specific telemetry must remain behind the integration boundary and must not become a substitute for the platform's canonical domain state.

## 12. Error Taxonomy

Operational evidence must distinguish at least:

- validation/client errors;
- authentication/authorisation failures;
- domain/business rule failures;
- dependency failures;
- timeout failures;
- concurrency/conflict failures;
- event/message processing failures;
- configuration failures; and
- unexpected/programming failures.

Stable machine-readable error codes should be used where the API or operational layer needs classification. Human-readable messages remain diagnostic text and must not be treated as the machine contract.

## 13. Failure, Retry and Incident Evidence

Retries must be visible rather than appearing as independent unexplained requests.

When an operation fails repeatedly, telemetry should allow operators to answer:

- What failed?
- When did it begin?
- Which service or dependency failed?
- Which customer/process was affected, within privacy constraints?
- What was retried?
- What was the final outcome?
- Was a fallback or degradation path used?
- Did an event enter a dead-letter path?
- Did an automated defence or containment control activate?

Incident response evidence must preserve the relevant correlation chain without requiring access to raw sensitive data.

## 14. Privacy and Security Controls

Observability infrastructure is itself a protected platform capability.

Controls include:

- least-privilege access;
- role-based access to sensitive telemetry;
- encryption in transit and at rest;
- retention policies by evidence class;
- redaction and tokenisation where appropriate;
- controlled export;
- access auditing;
- environment separation; and
- protection against telemetry tampering.

Development telemetry must never weaken production security boundaries.

## 15. Retention and Evidence Classes

Retention must be governed by data class rather than by a single universal period.

| Evidence | Primary purpose | Retention principle |
|---|---|---|
| Debug logs | Development/diagnosis | Shortest practical period |
| Operational logs | Runtime diagnosis | Governed operational period |
| Metrics | Capacity/health trends | Longer aggregated retention |
| Traces | Causal diagnosis | Governed, potentially sampled |
| Security evidence | Security investigation | Policy/legal requirement |
| Business audit | Accountability/compliance | Domain/legal requirement |
| AI decision evidence | Trust/audit | Risk and policy dependent |

Exact retention periods are implementation and regulatory decisions and must not be invented at this architecture layer.

## 16. Sampling and Cardinality

High-volume telemetry must be sampled or aggregated where full retention is not operationally justified.

Sampling must not remove the evidence required for:

- security incidents;
- financial disputes;
- material state transitions;
- AI authority decisions;
- human approvals; or
- regulated audit obligations.

High-cardinality labels such as unrestricted customer IDs must not be added to metrics merely for convenience.

## 17. Operational Dashboards

Operational dashboards should be organised around service and business health rather than individual log streams.

Minimum views should include:

1. platform health;
2. API/service health;
3. event infrastructure health;
4. database/storage health;
5. external dependency health;
6. commerce health;
7. fulfilment/delivery health;
8. security and abuse signals; and
9. AI Society health and authority activity.

Dashboards are derived views. They do not become sources of truth.

## 18. Alerting

Alerts should represent actionable conditions, not every error.

Alert classes should include:

- availability degradation;
- sustained latency degradation;
- elevated error rates;
- event backlog/dead-letter growth;
- dependency outage;
- database/storage saturation;
- security anomalies;
- material business-process failure; and
- AI governance or authority anomalies.

Every production alert should map to an operational response or investigation path.

## 19. Data Ownership

The observability platform owns telemetry infrastructure and derived operational evidence.

It does not become the authoritative owner of:

- customer accounts;
- products;
- inventory;
- baskets;
- orders;
- payments;
- refunds;
- fulfilment records; or
- AI domain state.

Domain services remain authoritative for their own state.

## 20. Service Implementation Requirements

Every backend service must define:

- health/readiness endpoints where appropriate;
- structured logging;
- request correlation;
- metrics;
- trace propagation;
- stable error classification;
- dependency instrumentation;
- audit hooks for material state changes; and
- operational failure signals.

Critical asynchronous workers must additionally expose queue depth/lag, processing rate, failure rate, retry activity and dead-letter activity.

## 22. Architectural Invariants

The following are non-negotiable:

1. A material backend action must be attributable.
2. Distributed operations must remain correlatable across synchronous and asynchronous boundaries.
3. Audit evidence must not depend solely on ordinary application logs.
4. Sensitive data must not be copied into telemetry without a justified need.
5. AI actions must expose capability and authority context.
6. Domain ownership must not be transferred to the observability platform.
7. Operational telemetry must not become an undocumented API or data contract.
8. Failure and degradation must be diagnosable.
9. Production telemetry access must itself be controlled and auditable.
10. Observability must survive service growth, multi-store expansion and AI Society scale.

## 23. Acceptance Criteria

Phase 3.13 is architecturally satisfied when:

- every critical service has a defined telemetry model;
- request and event correlation is preserved;
- material domain actions have durable audit evidence;
- errors have stable machine-readable classifications where required;
- external dependency failures are visible at integration boundaries;
- AI actions are attributable and authority-aware;
- telemetry access and retention are governed;
- alerting is tied to actionable operational conditions; and
- the resulting evidence is sufficient to reconstruct material incidents without requiring unrestricted access to sensitive production data.

## 25. Decision

Essentials Mart will implement observability as a first-class backend platform capability spanning logs, metrics, traces, audit evidence, event telemetry, AI decision evidence and operational alerting.

The system will favour **correlated, structured and purpose-bound evidence** over indiscriminate logging. The goal is not to record everything; the goal is to retain enough trustworthy evidence to understand, operate, secure and audit the platform at enterprise scale.
